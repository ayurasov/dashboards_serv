# Release notes — v0.4.1

Ветка `v0.4.1` от `v0.4.0`. Исправление запуска в Docker; схема базы, интерфейс и настройки не меняются, миграций нет.

## Для сотрудников

Изменений нет.

## Для администраторов

- **Запуск с `.env` по умолчанию.** В 0.4.0 контейнер `app` не становился здоровым, если `WEB_CONCURRENCY` в `.env` пустой (так в `.env.example`): `docker-compose.yml` передаёт переменную всегда, а gunicorn читает её как число ещё до своего файла настроек и с пустой строкой не запускается. Признаки — `dependency failed to start: container …-app-1 is unhealthy` при `docker compose up -d` и `ValueError: invalid literal for int() with base 10: ''` в `docker compose logs app`. Теперь точка входа контейнера убирает пустую переменную, и действует значение по умолчанию — 2 × ядра + 1, не больше 9. Обход в 0.4.0 — число в `WEB_CONCURRENCY`.
- **Переход со старой версии** («Dashboards API 1.1», SQLite) — проверенный порядок в «Руководстве по развёртыванию» и регламенте `upgrade-to-0.1.0.md`: остановить старый контейнер `dashboards_serv`, найти том `<папка>_db_data`, получить код в чистой папке через `git clone` (оставшиеся файлы старой версии — например, `frontend/src/router.js` — ломают сборку интерфейса), перенести копию базы в PostgreSQL командами с `-u root`.

## Обновление

```bash
docker compose exec -T db pg_dump -U dashboards -d dashboards -Fc > before-0.4.1.dump
git fetch && git checkout v0.4.1
docker compose up -d --build
```

Подробно — `docs/runbooks/upgrade-to-0.4.1.md`; откат — `git checkout v0.4.0 && docker compose up -d --build` с числом в `WEB_CONCURRENCY`.

## Проверено

- Сборка образа и запуск `docker-compose.yml` с `.env` по умолчанию (пустой `WEB_CONCURRENCY`): `app` — healthy, `worker` — running, `/api/health` — `ok`, вход администратора.
- Переход с базы старой версии из истории репозитория на PostgreSQL командами из руководства в контейнерах: пользователи и данные служб перенесены.
- Тесты сервера (SQLite и PostgreSQL), интерфейса и e2e.
