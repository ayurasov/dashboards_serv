# Наблюдаемость: журналы, здоровье, разбор инцидентов

Как понять, что происходит в «Дашбордах компании», и найти причину сбоя. Инструментов немного —
и все честно описаны ниже: метрик и трейсинга нет, опора — структурные журналы и статусы в базе.

## Здоровье за 30 секунд

| Что проверить | Как |
| --- | --- |
| Приложение и база | `curl -s http://<адрес>/api/health` — `status: ok`, версия, состояние БД и схема (`current` = `head`) |
| Контейнеры | `docker compose ps` — `app` и `db` здоровы по healthcheck; `worker` — по файлу-сердцебиению (обновляется каждым тактом, 30 с) |
| Планировщик | `docker compose logs worker --tail 5`: строка «Планировщик запущен» и отсутствие повторяющихся исключений; отметка о последнем такте — на экране «Входящие → Папка» |
| Очередь входящих | Тот же экран: файлы «дописываются» дольше `INBOX_SETTLE_SECONDS` — нормально; застряли надолго — смотрите журнал `worker` |

## Журналы

Оба сервиса пишут в stdout (`docker compose logs -f app` / `worker`); `LOG_JSON=true` — строки JSON
для сборщиков логов. У каждого API-запроса есть `X-Request-ID` (заголовок ответа; можно передать свой
в заголовке запроса) — он же попадает в запись журнала:

```
2026-11-20 12:01:02 INFO app.http: POST /api/inbox → 201 (30.3 мс) request_id=…
```

Найти запрос в журнале: скопируйте `X-Request-ID` из ответа (вкладка «Сеть» в браузере) и ищите
`docker compose logs app | grep <request_id>`. У ошибок коннекторов в журнале — полный traceback
(в интерфейсе виден только краткий текст).

**Гигиена прикладывания к тикетам**: не вставляйте в тикеты и чаты cookie сессий, значения `ds_csrf`,
заголовки `Authorization`, тела запросов с секретами подключений и строки подключения к базе.
`X-Request-ID`, путь, время и фрагмент журнала без секретов — достаточно.

## Внутренние журналы приложения (в базе)

- **Журнал изменений** («Администрирование → Журнал изменений») — кто, что и когда менял в справочниках
  и доступе; пригоден и как аудит, и как ответ «кто сломал порог светофора».
- **Журнал запусков подключений** («Интеграции» → карточка подключения) — статусы запусков
  по расписанию и вручную: `ok · partial · error`, счётчики и подробности по-русски.
- **Входящие данные** — у каждого элемента план и результат применения, повторы по SHA-256.

## Частые картины

| Симптом | Вероятная причина | Куда смотреть |
| --- | --- | --- |
| `app` не становится здоровым | миграции не применились / база недоступна | `docker compose logs app` — строки Alembic и ошибки БД |
| `worker` unhealthy | планировщик не пишет сердцебиение: остановился на долгом такте или упал | `docker compose logs worker --tail 50` |
| «Внутренняя ошибка коннектора» у «Папки» | нет прав на INBOX_DIR (чужой uid при bind-mount) | журнал `app`: PermissionError; права и владелец папки |
| Данные «не приезжают» по расписанию | подключение выключено, срок не наступил или запуск с ошибкой | журнал запусков подключения, `next_run` на карточке |
| 503 «Сервер перегружен» | пул соединений к БД исчерпан (`DB_QUEUE_TIMEOUT`) | число процессов `WEB_CONCURRENCY`, настройки пула; нагрузочный отчёт |

## Чего нет (осознанно)

Метрик Prometheus, трейсинга и алертинга в продукте нет — внешние проверки живости делает
эксплуатационный контур (например, Uptime Kuma на `/api/health`). Пределы производительности —
в [нагрузочных отчётах](../performance/load-test-0.4.0.md).
