# ADR-0011. Интеграции и входящие данные

- Статус: принято
- Дата: 2026-11-01
- Версия: 0.4.0
- Связано: ADR-0007 (структура), ADR-0008 (пользователи), ADR-0010 (сквозные отчёты); соглашения интеграций «По Делу» ↔ «Пульс проекта» (ADR-0055 «По Делу», ADR-0009/0010 «Пульса»); подключения к Jira и Confluence — как в burndown_tool

## Контекст

Данные в 0.1.0–0.3.0 попадают в систему вручную: форма или загрузка xlsx на странице службы. Источники в компании другие: выгрузки 1С, почта, вложения задач в «По Делу», проекты в «Пульсе», Jira, Bitrix24. Нужны: единый и прозрачный путь любых данных в систему; подключения к корпоративным системам с проверкой, расписанием и журналом; структура и пользователи из «По Делу».

## Решение

### 1. Входящие данные — единый конвейер

Любой файл или набор данных, откуда бы он ни пришёл, становится **элементом входящих** (`inbox_items`) и проходит один путь:

1. **Получение** — источник: папка «Входящие» на сервере, вложение задачи «По Делу», письмо в почтовом ящике (Exchange), загрузка в интерфейсе, приём по API с ключом интеграции, выгрузка коннектора (1С, Bitrix24, Jira…). Повтор того же файла (SHA-256) распознаётся и не применяется дважды.
2. **Распознавание набора** — по подпапке, правилу имени файла или содержимому: месяц службы персонала, приёмы и увольнения, недельный отчёт ТП, заявки Naumen, партнёрства, значения показателей, структура, сотрудники.
3. **План** — тот же движок, что у ручной загрузки этого набора (что создастся, изменится, ошибки); без записи в базу.
4. **Применение** — автоматически, если план без ошибок и для источника и набора включено «применять сразу», иначе — ожидает подтверждения на экране «Входящие» (план → «Применить» / «Отклонить»). Применение одной транзакцией, с записью в журнал изменений от имени источника.
5. **Итог** — статус элемента (получен · распознан · ожидает · применён · отклонён · ошибка · повтор), план и результат хранятся; исходный файл хранится до срока хранения (`INBOX_RETENTION_DAYS`).

Папка «Входящие» (`INBOX_DIR`, том Docker): подпапки по наборам (`hr-months/`, `hr-events/`, `tp-weekly/`, `naumen/`, `partnerships/`, `indicators/`, `structure/`, `employees/`) или корень с распознаванием; обработанные файлы переносятся в `processed/ГГГГ-ММ/` или `rejected/` вместе с отчётом `*.result.json`. Файл берётся в работу, когда не меняется дольше `INBOX_SETTLE_SECONDS` (дописывается — не трогаем).

Приём по API: `POST /api/inbound/v1/files` (multipart `file`, необязательные `dataset`, `apply`) с заголовком `Authorization: Bearer dash_…` — так 1С, скрипты и другие системы кладут данные без папки и почты; `GET /api/inbound/v1/ping`.

### 2. Каркас подключений

- `integrations` — подключение: вид (`podelu`, `puls`, `jira`, `confluence`, `bitrix24`, `exchange`, `onec`), название, включено, настройки (JSON без секретов), секреты (зашифрованы ключом, производным от `SECRET_KEY`; в API — только `has_secret`), расписание (интервал в минутах или время суток), состояние (`last_ok_at`, `last_error_at`, `last_error`).
- `integration_runs` — запуск: подключение, повод (вручную · по расписанию · вебхук · папка), начало, конец, итог (успех · частично · ошибка), сводка (счётчики), текст ошибки; хранится последние N запусков.
- Коннектор — класс с методами `check()` (проверка подключения: адрес, доступ, версия), `run(kind)` (синхронизация: структура, пользователи, данные, публикация) и описанием настроек для интерфейса. Коннектор не пишет в таблицы служб сам — он отдаёт данные в конвейер входящих или в источник показателей.
- Сетевые правила, общие для всех: адрес `http(s)://host[:port][/path]` без логина, `?` и `#`; разрешённые узлы `<ВИД>_ALLOWED_HOSTS` (`.domain` — домен и поддомены); перенаправления — ошибка с адресом; таймауты 5 с соединение / 30 с чтение; ответ не больше 20 МБ, только ожидаемый формат; повтор только при 429/503 (до 3 раз, `Retry-After` ≤ 10 с); прокси из `HTTPS_PROXY`; «не проверять сертификат» — явный флажок; подробные ошибки — администратору при проверке, краткие — остальным.
- Секрет привязан к адресу: при смене адреса секрет нужно ввести заново.
- **Планировщик** — отдельный процесс `python -m app.cli worker` (сервис `worker` в docker-compose, тот же образ): опрос папки «Входящие», запуски по расписанию, публикации. Запуск «занимается» атомарно в базе (`UPDATE … WHERE next_run_at <= now`) — несколько экземпляров не выполнят одно дважды. Без отдельного процесса всё доступно вручную и командой `python -m app.cli integrations run <id>` для cron.
- Ключи для входящих вызовов (`dash_` + `token_urlsafe(32)`), как в соглашениях «По Делу» и «Пульса»: показываются один раз, хранятся SHA-256 и префикс, сравнение `compare_digest`, «выпустить заново» заменяет, «отозвать» удаляет, ограничение частоты по ключу, область ключа — приём файлов и/или чтение статусов.

### 3. Коннекторы 0.4.0

| Система | Что берём / отдаём | Как подключаемся |
| --- | --- | --- |
| **«По Делу»** | структура и сотрудники (форматы `podelu.org-structure` и `podelu.employees` → план структуры и сотрудников 0.2.0, сопоставление по email и `external_id`); данные — вложения задач выделенного списка (и/или с меткой) → входящие, задача отмечается обработанной комментарием | сейчас — служебная учётная запись «По Делу» (вход, CSRF, выход после работы; как синхронизация структуры в «Пульсе»), права: `org.manage`, `users.manage`, участник только выделенного списка; режим ключа интеграции — когда «По Делу» поддержит ключи для нескольких систем |
| **«Пульс проекта»** | проекты: прогресс, выполнено/всего, просрочено, в работе, заблокировано, ближайшая веха, направление → вычисляемые показатели сквозного отчёта (по подразделениям через сопоставление «направление → подразделение»), светофор проекта выводится у нас | служебная учётная запись «Пульса» (сессия, только чтение); режим ключа — когда «Пульс» поддержит несколько ключей |
| **Jira** | показатели по JQL: число задач или сумма поля (оценка, остаток, затраты в часах) — на подразделение по шаблону JQL, помесячно; признаки качества данных (как в burndown) | Cloud (email + API token, `/rest/api/3`), Server/DC (PAT или логин/пароль, `/rest/api/2`), `JIRA_ALLOWED_HOSTS` |
| **Confluence** | публикация сквозного отчёта страницей по расписанию (обновление той же страницы или новая еженедельно), макросы статуса | как в burndown: `/rest/api/content`, поиск по id → по названию → создание, `CONFLUENCE_ALLOWED_HOSTS` |
| **Bitrix24** | сделки CRM: сумма и число по стадиям и ответственным (→ подразделения) за месяц → финансовые показатели; ссылки партнёрств | входящий вебхук REST (`https://портал/rest/<user>/<код>/crm.deal.list`), постранично по 50 |
| **Exchange** | письма в выделенной папке ящика: вложения → входящие (отправитель из разрешённого списка), письмо помечается прочитанным и переносится; позже — рассылка статусов | EWS (Exchange Server) через `exchangelib` или Microsoft Graph (Microsoft 365); IMAP как запасной путь |
| **1С** | выгрузки (ЗУП, Бухгалтерия) — через входящие (папка или `POST /api/inbound/v1/files` из 1С); прямое чтение — стандартный OData-интерфейс 1С (`/odata/standard.odata/`) по настроенным запросам → значения показателей по подразделениям (сопоставление подразделений 1С по коду или названию) | OData + Basic, `ONEC_ALLOWED_HOSTS` |

### 4. Интерфейс

- «Входящие» (`/inbox`): элементы со статусом, источником, набором; план и применение; загрузка файла; фильтры; доступно `data.manage` (новое полномочие) и редакторам служб — для своих наборов.
- «Интеграции» (`/admin/integrations`): карточки систем — состояние, проверка, настройки, расписание, «Запустить», журнал запусков; ключи для входящих вызовов; папка «Входящие» и её правила.

## Последствия

- Ручная загрузка на страницах служб остаётся и использует тот же движок плана.
- Для полноценной интеграции по ключам «По Делу» и «Пульс» должны поддержать несколько входящих ключей (сейчас ключ один и занят партнёром) — это задачи в их репозиториях; до тех пор работает служебная учётная запись с минимальными правами.
- Новые зависимости: `cryptography` (шифрование секретов), `exchangelib` (Exchange, необязательная).
