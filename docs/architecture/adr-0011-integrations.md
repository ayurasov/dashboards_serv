# ADR-0011. Интеграции и входящие данные

- Статус: принято
- Дата: 2026-11-01, уточнено по реализации 2026-11-02
- Версия: 0.4.0
- Связано: ADR-0007 (структура), ADR-0008 (пользователи), ADR-0010 (сквозные отчёты); соглашения интеграций «По Делу» ↔ «Пульс проекта» (ADR-0055 «По Делу», ADR-0009/0010 «Пульса»); подключения к Jira и Confluence — как в burndown_tool

## Контекст

Данные в 0.1.0–0.3.0 попадают в систему вручную: форма или загрузка xlsx на странице службы. Источники в компании другие: выгрузки 1С, почта, вложения задач в «По Делу», проекты в «Пульсе», Jira, Bitrix24. Нужны: единый и прозрачный путь любых данных в систему; подключения к корпоративным системам с проверкой, расписанием и журналом; структура и пользователи из «По Делу».

## Решение

### 1. Входящие данные — единый конвейер

Любой файл или набор данных, откуда бы он ни пришёл, становится **элементом входящих** (`inbox_items`) и проходит один путь:

1. **Получение** — источник: папка «Входящие» на сервере (`folder`), загрузка в интерфейсе (`upload`), приём по API с ключом (`api`), подключение (`integration`: вложение задачи «По Делу», вложение письма, структура «По Делу»). Размер — до `INBOX_MAX_MB`; SHA-256 содержимого. Подключение может дать элементу пояснение для человека (`note`, до 500 символов): «Задача «…» · автор», «Письмо «…» от …».
2. **Распознавание набора** — по подпапке, выбору при загрузке, параметру `dataset` API или правилу подключения; иначе по содержимому: каждый набор оценивает первые строки таблицы или разобранный JSON (0–100), совпадение имени с шаблоном набора добавляет 20; берётся лучший набор с оценкой не меньше 50, при равенстве лучших — не распознан. JSON других систем подключается `register_json_format` (`podelu.org-structure` → «Структура компании», `podelu.employees` → «Сотрудники»): документ переводится в наш формат до плана. Наборы: `hr-months` (метрики месяцев службы персонала), `hr-events` (приёмы и увольнения), `tp-weekly` (недельный отчёт ТП), `naumen` (заявки Naumen SD), `partnerships` (реестр партнёрств), `indicators` (значения показателей), `structure` (структура компании), `employees` (сотрудники).
3. **План** — тот же движок, что у ручной загрузки этого набора (что создастся, изменится, ошибки); без записи в базу.
4. **Применение** — автоматически, если план без ошибок и для источника и набора включено «применять сразу» (`inbox_rules`, только для `folder`, `api`, `integration`; загрузку применяет загрузивший), иначе — ожидает подтверждения на экране «Входящие» (план → «Применить» / «Отклонить»). Перед применением файл разбирается и план строится заново по текущим данным; применение — одной транзакцией в точке сохранения, при ошибках плана ничего не записывается (409 `import_has_errors` со свежим планом). Журнал изменений — от имени источника: «временный» пользователь со всеми службами и классами данных и полномочиями `org.manage` и `reports.manage`, без роли администратора и без `users.manage` (роли, профили и вход по домену из файлов не выдаются); пользователь с `data.manage` применяет с правами источника, но журнал пишется на него; остальные — со своими правами.
5. **Итог** — статус элемента (получен · распознан · ожидает · применён · отклонён · ошибка · повтор), план и результат хранятся. Повтор — тот же набор и SHA-256 у «живого» элемента (получен, распознан, ожидает, применён), частичный уникальный индекс `(dataset, sha256)` распознаёт его и при одновременном приёме; отклонённый и ошибочный файл можно прислать снова. Исходный файл завершённого элемента хранится `INBOX_RETENTION_DAYS` дней после обработки, ожидающие не очищаются.

Видимость и права: `data.manage` — все элементы, правила, папка; остальные — элементы наборов, которые они применяют (`Dataset.can_apply`: полномочие набора или уровень к его службе и класс данных), и свои загрузки. Набор `indicators` применяет любой пользователь с уровнем «Ввод данных» хотя бы к одной службе — права проверяются по строкам; чужие элементы этого набора видят только `reports.manage` и `data.manage` (план источника строится со всеми классами данных).

Папка «Входящие» (`INBOX_DIR`, в Docker — том `/data/inbox`): подпапки по наборам (`hr-months/`, `hr-events/`, `tp-weekly/`, `naumen/`, `partnerships/`, `indicators/`, `structure/`, `employees/`) или корень с распознаванием; обработанные файлы переносятся в `processed/ГГГГ-ММ/` (принятые) или `rejected/` (ошибка, повтор, слишком большой) вместе с отчётом `*.result.json`. Файл берётся в работу, когда не меняется дольше `INBOX_SETTLE_SECONDS`, и «занимается» атомарным переносом в `.work/`; временные и скрытые имена не берутся, символьные ссылки на файлы не открываются, подпапка-ссылка читается только внутри папки.

Приём по API: `POST /api/inbound/v1/files` (multipart `file`, необязательные `dataset`, `apply`, `options`) с заголовком `Authorization: Bearer dash_…` — так 1С, скрипты и другие системы кладут данные без папки и почты; `apply=false` — только план, иначе — по правилу; 201 — новый элемент, 200 — повтор. `GET /api/inbound/v1/files/{id}` — статус своих файлов, `GET /api/inbound/v1/ping` — проверка ключа. Сессия и CSRF не используются; ошибки — `{detail, code}` и те же значения в `{error, message}` (как в соглашениях «По Делу» и «Пульса»).

Значения показателей (`indicators`, а также `ctx.plans.indicator_values` коннекторов) поддерживают явную очистку: строка с `clear` («Очистить» = «да») без значения, цели и комментария удаляет сохранённое значение за месяц; пустое значение без `clear` ничего не стирает.

### 2. Каркас подключений

- `integrations` — подключение: вид, название, включено, настройки (JSON без секретов), секреты (зашифрованы), адрес привязки секретов (`secret_bound_url`, открыто — его видно в интерфейсе), расписание и следующий запуск, состояние коннектора между запусками (`state`: курсоры, id страницы), отметка проверки (`verified_at`), здоровье (`last_ok_at`, `last_error_at`, `last_error`), признак идущего запуска (`running_since`).
- `integration_runs` — запуск: действие, повод (вручную · по расписанию · командой), начало, конец, итог (успех · частично · ошибка), сводка (счётчики, номера элементов входящих, подробности), сообщение, текст ошибки, кто; хранится последние `INTEGRATION_RUNS_KEEP` (200) на подключение.
- Коннектор — класс с атрибутами `kind`, `title`, `description`, `fields`, `actions`, `url_field`, `singleton` и методами `check()` (адрес, вход, права, версия, нужные объекты), `run(action, ctx)` и `validate_config()`. Поля настроек описываются для интерфейса: типы `string` · `text` · `url` · `password` · `int` · `bool` · `select` · `multiselect` · `list` · `time` · `json` (разобранный JSON — списки правил и запросов, до 64 КБ; принимается и JSON-текст, ошибка — с номером строки и позиции), `required`, `secret`, `default`, `placeholder`, `min`/`max`, `options`, `show_if`. Действие — `schedulable` или только вручную. Коннектор не пишет в таблицы служб сам — он отдаёт файлы в конвейер входящих (`ctx.inbox.add`) или строки движкам загрузки (`ctx.plans.structure`, `employees`, `org_list`, `indicator_values`) и создаёт недостающие показатели каталога функцией каталога (`ctx.plans.ensure_indicator`).
- Включить подключение можно только после успешной проверки текущих настроек (409 `check_required`); изменение настроек или секретов снимает отметку проверки.
- Сетевые правила, общие для всех (`HttpClient`): адрес `http(s)://host[:port][/path]` без логина, `?` и `#`; разрешённые узлы `<ВИД>_ALLOWED_HOSTS` (`.domain` — домен и поддомены, пусто — без ограничения), проверяются и при сохранении настроек; перенаправления — ошибка с адресом; тайм-ауты 5 с соединение / 30 с чтение; ответ не больше 20 МБ, JSON проверяется по виду; повтор при 429/503 (до 3 раз, `Retry-After` ≤ 10 с) — только у безопасных запросов (GET, HEAD, OPTIONS), запросы, меняющие данные у партнёра (вход, комментарий, публикация), не повторяются; прокси из `HTTPS_PROXY` / `HTTP_PROXY`; «не проверять сертификат» — явный флажок; ошибки — с кодом и двумя текстами: подробным для администратора и кратким для остальных.
- Секреты: Fernet, ключ — `urlsafe_b64(sha256("integration:" + SECRET_KEY))`; в API — только `has_secret`, `secret_fields`, `secret_problem`. Секрет привязан к адресу, на который он уходит, и к подключению (адрес и владелец `integration:<id>` — и открыто, и внутри шифротекста): при смене адреса секрет нужно ввести заново (422 `secret_rebind_required`), сохранённый токен никогда не уходит на другой адрес. Адрес привязки по умолчанию — поле `url_field`; коннектор, чей секрет уходит на несколько адресов или на адрес, зависящий от режима, переопределяет `secret_url()` и перечисляет поля в `secret_url_fields`: «По Делу» — адрес и адрес для запросов сервера, почтовый ящик — адрес EWS, адреса входа и Graph с тенантом или `imap(s)://сервер:порт`. Смена `SECRET_KEY` делает секреты нечитаемыми (подключение показывает «введите секрет заново»), перешифрование в 0.4.0 не поддерживается. Значения секретов, пароль Basic, токен из Authorization, логин и пароль в адресе и сегменты пути, равные секрету (код вебхука Bitrix24), вычищаются из текстов ошибок, журнала запусков и журнала сервера.
- **Планировщик** — отдельный процесс `python -m app.cli worker` (сервис `worker` в docker-compose, тот же образ и переменные, общий том папки): такт `WORKER_TICK_SECONDS` — опрос папки «Входящие», запуски по расписанию, раз в час — срок хранения, отметка о работе (`app_settings.worker_status`, её показывает экран «Входящие → Папка»). Планировщик не мигрирует схему — ждёт, пока её обновит `app`; SIGTERM доделывает такт. Запуск «занимается» атомарно в базе (`UPDATE … WHERE next_run_at <= now`), идущий запуск — `running_since` тем же приёмом (запуск старше двух часов считается прерванным) — несколько экземпляров не выполнят одно дважды. Ручной запуск выполняется в процессе приложения синхронно. Без отдельного процесса всё доступно вручную и командами `python -m app.cli inbox scan`, `inbox cleanup`, `integrations run <id|вид>` для cron.
- Расписание: вручную, интервал (5 минут — неделя) или время ЧЧ:ММ по `TIMEZONE` с днями недели; по расписанию выполняются выбранные `schedulable` действия.
- Ключи для входящих вызовов (`dash_` + `token_urlsafe(32)`), как в соглашениях «По Делу» и «Пульса»: показываются один раз, хранятся SHA-256 и префикс (12 символов), сравнение `compare_digest`, «выпустить заново» заменяет значение того же ключа, «отозвать» отмечает ключ отозванным (запись остаётся для журнала и элементов входящих), `last_used_at` — не чаще раза в минуту, ограничение частоты по ключу (`INBOUND_RATE_LIMIT` в минуту, счётчик в памяти процесса), область ключа — приём файлов (`files`) и/или чтение статусов (`status`).
- Ссылки наружу (страница Confluence, комментарий «По Делу») строятся от `PUBLIC_URL`; пусто — без ссылок.

### 3. Коннекторы 0.4.0

| Система | Что берём / отдаём | Как подключаемся |
| --- | --- | --- |
| **«По Делу»** (`podelu`) | «Синхронизировать структуру»: `podelu.org-structure` → элемент входящих набора «Структура» (план и применение — по правилу «Подключение × Структура»; сопоставление по пути, внешний ID — ключ подразделения; неизвестные типы уровней → тип по умолчанию; настройки структуры не применяются, недостающие подразделения создаются по настройке); `podelu.employees` и `users/admin/all` → быстрая загрузка списком с источником `podelu` (сопоставление по id «По Делу», затем email; новые — «Без доступа»; роли, полномочия и активность не переносятся; применение — только при совпадающей структуре и правиле «Подключение × Сотрудники», строки с ошибками пропускаются; «Отключать отсутствующих» — только пришедших из «По Делу», не служебную учётную запись). «Забрать данные из задач»: вложения (Excel, CSV, JSON) задач выделенного списка и меток и их результатов → входящие с `source_ref podelu:<задача>:<вложение>:<sha256>` и пояснением «Задача «…» · автор»; задача отмечается комментарием «Файл «…» принят в «Дашборды»: <статус>» и ссылкой на «Входящие» (`PUBLIC_URL`); курсор — `updatedAt` и число вложений задач | служебная учётная запись «По Делу» (CSRF-токен, вход с Referer и Origin, выход всегда — и после ошибки); права: `org.manage`, `users.manage`, участник только выделенного списка; основной адрес и необязательный адрес для запросов сервера — секрет привязан к обоим. Режима ключа нет: «По Делу» выдаёт один входящий ключ, и он занят «Пульсом» |
| **«Пульс проекта»** (`puls`) | «Обновить показатели проектов» за текущий месяц: `puls.projects` (в работе), `puls.overdue` (просроченные), `puls.on_time_share` (доля в срок), `puls.progress` (средний прогресс), `puls.blocked` (заблокированные задачи) по подразделениям через «направление → подразделение» (несопоставленные — в корень; подразделение, вышестоящие и корень — по своей ветке); показатели создаются в каталоге при первом запуске (вводимые, операционные, служба-владелец — проектный и продуктовый офис), значения — через `indicator_values`, неопределённые (нет проектов в работе) очищаются строкой `clear`; светофор проекта выводится у нас: красный — просрочен, жёлтый — заблокированные задачи или ≤ 14 дней до окончания при прогрессе < 80 %, зелёный — остальные, серый — без задач | служебная учётная запись «Пульса» (сессия, только чтение, выход всегда). Режим ключа (`Bearer puls_…`, `/api/integration/v1/ping` и `/projects`) заготовлен в настройках: «Пульс» пока выдаёт один ключ, занятый «По Делу»; в этом режиме нет заблокированных задач и id направлений, не больше 200 проектов |
| **Jira** (`jira`) | показатели по JQL — правила JSON: число задач или сумма поля (`timeestimate`, `timespent`, `timeoriginalestimate` — секунды в часы, или `customfield_*`) на подразделение — шаблон `jql` с `{unit_code}` и `units` или `unit_jql`; подстановки месяца; JQL без месяца — снимок в текущий месяц; окно «Месяцев к пересчёту»; не больше 5000 задач на JQL; признаки качества данных (как в burndown) в сводке; «Проверить правила без записи» | Cloud (email + API token, `/rest/api/3/search/jql`), Server/DC (PAT или логин и пароль, `/rest/api/2/search`), CAPTCHA объясняется; `JIRA_ALLOWED_HOSTS` |
| **Confluence** (`confluence`) | публикация сквозного отчёта (`reports.company_scorecard` — отчёт без пользователя) за последний завершённый месяц (со сдвигом) страницей: панель статуса с объяснением, таблицы подразделений и показателей с макросами статуса, нарушения полноты, заметки, ссылка на отчёт (`PUBLIC_URL`); полный отчёт как у администратора (вся компания или ветка), финансовые скрыты по умолчанию; режим «одна страница» (по сохранённому id → по названию → создание, версия + 1, на 409 — перечитать и повторить один раз) или «каждую неделю» | как в burndown: `/rest/api/content`, `CONFLUENCE_ALLOWED_HOSTS` |
| **Bitrix24** (`bitrix24`) | сделки CRM (`crm.deal.list`, постранично по 50, повтор на `QUERY_LIMIT_EXCEEDED`): выручка выигранных сделок и их число за месяц, воронка открытых сделок (снимок) → показатели по подразделениям ответственных (по email сотрудника или отделу Bitrix24, явное соответствие сильнее); обнуление исчезнувших значений, итоги веток; ссылки партнёрств — не в 0.4.0 | входящий вебхук REST (секрет, привязан к адресу портала), права «CRM» и «Пользователи» (+ «Структура компании») |
| **Почтовый ящик (Exchange)** (`exchange`) | письма выделенной папки от разрешённых отправителей (email или домен): вложения → входящие с пояснением «Письмо «…» от …», набор — по правилу «тема → набор» или распознаётся; письмо помечается прочитанным и/или переносится, курсор; до 100 писем за запуск; рассылка статусов — не в 0.4.0 | EWS (Exchange Server) через `exchangelib` (необязательная зависимость), Microsoft Graph (Microsoft 365, client credentials, `Mail.ReadWrite`) или IMAP — равноправные режимы |
| **1С** (`onec`) | выгрузки (ЗУП, Бухгалтерия) — через входящие (папка или `POST /api/inbound/v1/files` из 1С, пример функции — в описании коннектора); прямое чтение — стандартный OData-интерфейс 1С (`/odata/standard.odata/`) по настроенным запросам JSON (набор или виртуальная таблица, `$filter` с подстановками месяца, `sum` · `count` · `avg`, множитель) → значения показателей по подразделениям (сопоставление подразделений 1С по коду или наименованию справочника, явное соответствие сильнее); проверка сверяет наборы с `$metadata` | OData + Basic (UTF-8), `ONEC_ALLOWED_HOSTS` |
| **Папка «Входящие»** (`folder`) | разбор папки кнопкой «Разобрать папку» с журналом запусков; одно подключение на систему | без адреса и секретов |

Общее для коннекторов показателей (Jira, Bitrix24, 1С, «Пульс»): сначала план без записи, запись — только при новых, изменённых или очищаемых значениях (повторный запуск с теми же данными ничего не пишет — ни значений, ни журнала, ни ревизии отчётов); показатель из настроек, которого нет в каталоге, создаётся после получения данных для него (при неудачном запуске каталог не засоряется); вычисляемые и выключенные показатели не заполняются.

### 4. Интерфейс

- «Входящие данные» (`/inbox`): элементы со статусом, источником, набором и сводкой плана, чипы статусов, фильтры; карточка элемента — план любого набора, параметры набора, «Применить» / «Отклонить» / «Повторить»; загрузка файла; для `data.manage` — вкладки «Правила» (источник × набор) и «Папка» (состояние, «Проверить сейчас», планировщик, подпапки, справка по API и 1С). Доступно `data.manage` (новое полномочие «Входящие данные») и тем, кто применяет хотя бы один набор, — для своих наборов; счётчик ожидающих — в меню.
- «Интеграции» (`/admin/integrations`, новое полномочие `integrations.manage` «Интеграции»): карточки подключений — состояние, проверка, «Включено», действия «Запустить», расписание, журнал запусков; «Подключить систему» — все виды сервера, форма настроек строится по описанию полей; вкладка «Ключи для входящих вызовов». Страница «Вход по домену» переехала на `/admin/directory`.

## Последствия

- Ручная загрузка на страницах служб остаётся и использует тот же движок плана; появились загрузки метрик месяцев и реестра службы персонала и реестра партнёрств.
- Для полноценной интеграции по ключам «По Делу» и «Пульс» должны поддержать несколько входящих ключей (сейчас ключ один и занят партнёром) — это задачи в их репозиториях; до тех пор работает служебная учётная запись с минимальными правами, а каждый запуск — вход в систему партнёра (у «По Делу» — ограничение 10 входов в минуту и 50 в час с адреса).
- `SECRET_KEY` стал ключом шифрования: его смена требует ввести секреты подключений заново; переходный режим со старым ключом (`SECRET_KEY_PREVIOUS`) и перешифрование — задача следующих версий.
- Ограничение частоты приёма по API считается в памяти процесса: при нескольких процессах фактический предел выше; общий счётчик в базе — при необходимости.
- Ручной запуск подключения держит поток процесса приложения до конца запуска; долгие запуски ставятся в расписание планировщика.
- Подключение с полномочием «Интеграции» пишет данные от своего имени, а Confluence публикует полный отчёт — полномочие выдаётся только доверенным сотрудникам.
- Новые зависимости: `requests`, `cryptography` (шифрование секретов), `exchangelib` (Exchange, необязательная).
