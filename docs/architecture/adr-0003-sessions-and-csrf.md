# ADR-0003. Вход: серверные сессии в базе, httpOnly-cookie и CSRF-токен

- Статус: принято
- Дата: 2026-11-01
- Версия: 0.1.0

## Контекст

Прежняя версия выдавала JWT, который интерфейс хранил в `localStorage` и отправлял в заголовке. Такой токен читается любым скриптом страницы, его нельзя отозвать (смена пароля и отключение пользователя не завершали сессии), а срок жизни задавался только при выдаче. PDF скачивались обходным путём через `fetch` и `Blob`.

## Решение

- При входе создаётся запись `user_sessions`: в cookie `ds_session` (httpOnly, SameSite=Lax, `Secure` по `SESSION_COOKIE_SECURE`) — случайный токен 256 бит, в базе — только его SHA-256.
- Сессия ограничена сроком (`SESSION_LIFETIME_HOURS`) и простоем (`SESSION_IDLE_MINUTES`); отметка активности обновляется не чаще раза в 2 минуты.
- CSRF: токен сессии отдаётся в ответе входа и `/api/auth/me` и в читаемой cookie `ds_csrf`; изменяющие запросы обязаны прислать его в заголовке `X-CSRF-Token` (сравнение постоянного времени).
- Смена пароля завершает остальные сессии; сброс пароля администратором и отключение пользователя — все. Пользователь видит свои сессии в профиле и может завершить любую.
- Неудачные входы ограничены скользящим окном по паре «адрес + логин»; при неизвестном логине выполняется холостая проверка bcrypt, чтобы время ответа не выдавало существование учётной записи.
- Временный пароль (создание пользователя без пароля, сброс) обязывает сменить его: до смены сервер отвечает `403 password_change_required` на всё, кроме профиля и справки.
- Политика паролей: не короче `PASSWORD_MIN_LENGTH`, не только буквы или только цифры, не равен логину; bcrypt (12 раундов, в тестах — 4).

## Последствия

- Скрипты страницы не видят токен сессии; файлы скачиваются обычными запросами с cookie.
- Swagger UI (`/api/docs`) работает в той же вкладке после входа в приложение.
- Счётчик неудачных входов живёт в памяти процесса: при N процессах предел фактически до N раз выше — для защиты от подбора этого достаточно.
