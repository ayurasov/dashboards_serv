# ADR-0009. Модель доступа 2.0: профили доступа и индивидуальная настройка

- Статус: принято
- Дата: 2026-11-01
- Версия: 0.2.0
- Связано: ADR-0004 (модель доступа 0.1.0), ADR-0007 (структура компании), ADR-0008 (пользователи и вход по домену)

## Контекст

В 0.1.0 доступ задаётся уровнем к службе («Просмотр», «Ввод данных», «Управление») и признаком «только свои подразделения» для реестра службы персонала. Этого мало для дашбордов, которыми пользуется вся компания — от первого лица до рядовых сотрудников:

- руководство должно видеть верхнеуровневую картину по всей компании и, в зависимости от прав, «проваливаться» на нужную глубину;
- руководитель подразделения — свою ветку структуры целиком;
- рядовой сотрудник — только просмотр своего подразделения и никаких денежных показателей;
- права должны настраиваться индивидуально: одинаковых шаблонов на всех не бывает (куратор нескольких подразделений, финансовый контролёр без кадровых данных, руководитель с расширенной глубиной).

## Решение

Доступ пользователя складывается из **профиля доступа** (шаблон) и **индивидуальных настроек** поверх него. Каждое измерение доступа либо наследуется из профиля («как в профиле»), либо задано лично. Роль «Администратор» по-прежнему даёт полный доступ ко всему.

### Измерения доступа

| Измерение | Значения | Что ограничивает |
| --- | --- | --- |
| Уровень доступа к службе | нет · просмотр · ввод данных · управление | Разделы службы и действия в них (как в 0.1.0); «нет» явно запрещает службу, даже если профиль её даёт |
| Область структуры | вся компания · своя ветка · своё подразделение | Данные, привязанные к подразделениям: реестры, разрезы по подразделениям, показатели сквозных отчётов. Можно задать отдельно для службы |
| Дополнительные подразделения | список подразделений | Расширяет область: куратор, заместитель, проектный руководитель |
| Классы данных | операционные (всегда) · персональные · финансовые | Персональные — ФИО, должности, причины увольнения в реестрах; финансовые — денежные показатели (выручка, затраты, ФОТ, бюджеты) |
| Глубина детализации | 0…9 уровней или без ограничения | На сколько уровней структуры ниже вершины своей области можно раскрыть сквозной отчёт |
| Исходные записи | да · нет | Реестры и списки (приёмы и увольнения, недельный отчёт, реестр партнёрств) или только агрегаты и дашборды |
| Выгрузка | да · нет | Excel, CSV и PDF |

Вершина области — вся компания (область «вся компания») или подразделения пользователя: основное, руководимые и дополнительные. Глубина отсчитывается от вершины: у первого лица с глубиной 1 — компания и уровень под ней, у руководителя подразделения с глубиной «без ограничения» — вся его ветка.

### Профили доступа

Встроенные профили (изменяемые, но не удаляемые) соответствуют уровням сотрудников:

| Профиль | Область | Классы данных | Глубина | Записи | Выгрузка | Службы |
| --- | --- | --- | --- | --- | --- | --- |
| Высшее руководство | вся компания | все | 1 | нет | да | просмотр всех служб с дашбордами |
| Руководитель направления | своя ветка | все | 2 | да | да | просмотр всех служб с дашбордами |
| Руководитель подразделения | своя ветка | операционные, персональные | без ограничения | да | да | — |
| Специалист | своё подразделение | операционные | без ограничения | да | да | — (выдаются лично) |
| Сотрудник | своё подразделение | операционные | 0 | нет | нет | — |

Администратор создаёт свои профили (например, «Финансовый контролёр»: вся компания, операционные и финансовые, без персональных).

### Действующий доступ

Для каждого измерения: личное значение, если задано, иначе значение профиля, иначе — без профиля («Индивидуальная настройка») — значение по умолчанию, совместимое с 0.1.0 (вся компания, все классы, без ограничения глубины, записи и выгрузка разрешены). Уровни служб: личная строка доступа к службе, иначе уровень из профиля.

Карточка пользователя показывает действующий доступ с указанием источника каждого значения («из профиля „Руководитель подразделения“» / «задано лично»), профиль пользователя показывает действующий доступ ему самому.

### Хранение

- `access_profiles` — `key`, `name`, `description`, `is_system`, `sort_order`, `service_levels` (JSON `{служба: уровень}`), `org_scope`, `data_classes` (JSON), `drill_depth` (NULL — без ограничения), `can_view_records`, `can_export`.
- `user_access_policies` — одна строка на пользователя: `profile_id` (NULL — индивидуальная настройка) и личные значения тех же измерений (NULL — как в профиле), `drill_depth_unlimited` для явного «без ограничения» поверх профиля.
- `user_access_units` — дополнительные подразделения области.
- `service_access.level` допускает `none`; вместо `department_scope` — `org_scope` (NULL — как у пользователя). Миграция переносит `department_scope = true` в `org_scope = 'branch'`.

Существующие пользователи после миграции получают «Индивидуальную настройку» с прежними уровнями служб: их доступ не меняется.

### Проверки

- Сервер — источник правды: `app/services/access.py` вычисляет `EffectiveAccess` один раз на запрос (в `auth_context`); зависимости `require_service`, `require_records`, `require_export`, `require_data_class` и функция области `scope_units()` используют его.
- Интерфейс получает действующий доступ в `/api/auth/me` и скрывает недоступные разделы и кнопки; прямой запрос всё равно отклоняется сервером.
- Ключ кэша ответов включает действующую область и классы данных — разные права не получают чужой ответ из кэша.

## Последствия

- Сквозные отчёты 0.3.0 (ADR-0010) используют область, глубину и классы данных без изменения модели.
- Новая служба или новый тип данных описывается в `registry.py`: класс данных у показателя или раздела, уровень доступа у действия.
- Миграция 0014 не меняет доступ существующих пользователей; профили назначаются администратором или по группам каталога при первом входе по домену (ADR-0008).
