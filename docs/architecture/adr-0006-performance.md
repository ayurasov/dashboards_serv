# ADR-0006. Производительность: 500–1000 одновременных пользователей

- Статус: принято
- Дата: 2026-11-01
- Версия: 0.1.0
- Измерения: `docs/performance/load-test-0.1.0.md`, сценарий — `loadtest/`

## Контекст

Прототип работал одним процессом uvicorn на SQLite: аналитика пересчитывалась на каждый запрос, выгрузки и PDF выполнялись в том же процессе. Целевая нагрузка версии 0.1.0 — 500–1000 одновременно работающих сотрудников (дашборды, реестры, выгрузки, PDF) на сервере с 4 ядрами и PostgreSQL рядом.

Первые прогоны нагрузочного сценария выявили три проблемы:

1. **Соединения PostgreSQL.** 9 процессов × (10 постоянных + 10 дополнительных) соединений превышали `max_connections` = 100: под нагрузкой база отказывала в подключении.
2. **Повторные вычисления.** Аналитика дашбордов (персонал, техподдержка, партнёрства, Naumen) пересчитывалась для каждого пользователя, хотя данные меняются редко — несколько загрузок в неделю.
3. **Взаимная блокировка потоков и соединений.** Синхронные обработчики FastAPI выполняются в пуле потоков процесса, причём в пул попадает не только обработчик, но и проверка прав, сериализация ответа и закрытие сессии. При 1000 пользователях все потоки занимали запросы, ждущие соединение из пула, а запросы с соединением ждали свободный поток, чтобы сериализовать ответ и вернуть соединение. Соединения по 100+ секунд висели в состоянии `idle in transaction`, запросы завершались по тайм-ауту пула (`QueuePool limit … timed out`).

## Решение

### Процессы и соединения

- gunicorn + uvicorn-worker: `WEB_CONCURRENCY` процессов (по умолчанию 2 × ядра + 1, не больше 9), перезапуск процесса после `GUNICORN_MAX_REQUESTS` запросов.
- Пул соединений на процесс: `DB_POOL_SIZE=5` + `DB_MAX_OVERFLOW=4`. При 9 процессах — не больше 81 соединения, в пределах `max_connections` = 100 с запасом на миграции и обслуживание.

### Очередь запросов к базе (главное)

- Сессию базы данных запрос получает через зависимость `get_db`, и только когда в процессе меньше `DB_CONCURRENCY` (по умолчанию — `DB_POOL_SIZE + DB_MAX_OVERFLOW`) запросов, работающих с базой. Остальные ждут в асинхронной очереди — без потока и без соединения. Запросов с сессией не больше, чем соединений, а потоков (`THREADPOOL_SIZE`, по умолчанию соединения + 8) больше, чем таких запросов, — поэтому ни соединений, ни потоков им всегда хватает, и взаимная блокировка невозможна по построению.
- Дольше `DB_QUEUE_TIMEOUT` (30 с) запрос в очереди не ждёт: ответ 503 `overloaded` с `Retry-After: 5` вместо зависания.
- Проверка сессии, CSRF и загрузка пользователя с правами — одна синхронная зависимость (`auth_context`) с одной транзакцией; проверки уровня доступа — асинхронные, без обращений к базе.
- Закрытие сессии выполняется в отдельном небольшом пуле потоков и не ждёт общий пул.
- Вход: соединение возвращается в пул до проверки пароля (bcrypt, ~0,3 с процессорного времени).
- PDF: не больше `PDF_CONCURRENCY` (2) отчётов строится в процессе одновременно; очередь отчётов — асинхронная и стоит раньше очереди к базе, поэтому ожидающий отчёт не занимает ни поток, ни место в очереди к базе.

### Кэш ответов

- Ответы аналитики кэшируются в памяти процесса (LRU, `RESPONSE_CACHE_SIZE` = 512) по ключу «запрос + права пользователя + ревизия данных службы». Ревизия (`data_revisions`) увеличивается в той же транзакции, что и любое изменение данных службы (через журнал изменений), поэтому кэш всех процессов становится неактуальным одновременно и без рассылки сообщений.
- Для ответов от 2 КБ кэш хранит и сжатую gzip-версию: повторное сжатие не выполняется.
- Кэш можно отключить: `RESPONSE_CACHE=false`.

## Последствия

- Конфигурация по умолчанию выдерживает 1000 одновременных пользователей на 4 ядрах без ошибок сервера; результаты и методика — `docs/performance/load-test-0.1.0.md`.
- Узкое место при росте — процессор (bcrypt при массовом входе, построение PDF); масштабирование — больше процессов, затем больше экземпляров приложения за балансировщиком (сессии хранятся в базе).
- При увеличении `WEB_CONCURRENCY`, `DB_POOL_SIZE` или `DB_MAX_OVERFLOW` нужно проверить, что `WEB_CONCURRENCY × (DB_POOL_SIZE + DB_MAX_OVERFLOW)` меньше `max_connections` PostgreSQL.
- Новые обработчики работают с базой только через `get_db`; длительную работу без базы (вычисления, внешние вызовы) выполняют после `db.commit()`, чтобы не держать соединение.
