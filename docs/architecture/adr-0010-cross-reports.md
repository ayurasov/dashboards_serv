# ADR-0010. Сквозные отчёты, светофоры и статусы по уровням сотрудников

- Статус: принято
- Дата: 2026-11-01
- Версия: 0.3.0 (проект начат в 0.2.0)
- Связано: ADR-0007 (структура компании), ADR-0009 (модель доступа 2.0)

## Контекст

Дашборды 0.1.0–0.2.0 построены по службам: каждый показывает свою предметную область целиком. Руководству нужна единая картина компании «сверху вниз»: общий статус, из чего он складывается и где проблема — с возможностью раскрыть уровень структуры и показатель на нужную глубину. Рядовым сотрудникам нужен статус своего подразделения без денежных показателей. Состав и глубина видимого у каждого свои (ADR-0009).

## Решение

### Показатели

Каталог показателей (`indicators`) ведёт сотрудник с полномочием `reports.manage` (или администратор). Каждый показатель задаёт:

| Поле | Значения |
| --- | --- |
| ключ, название, описание, единица | — |
| класс данных | операционный · персональный · финансовый (ADR-0009) |
| направление | больше — лучше · меньше — лучше · без оценки |
| свёртка по структуре | сумма · среднее · без свёртки (только собственные значения уровня) |
| правило светофора | пороги (зелёный / жёлтый, как в 0.1.0) или отклонение от цели в % (в пределах X % — зелёный, Y % — жёлтый, дальше — красный) |
| цель по умолчанию | число или пусто; цель уровня и периода задаётся вместе со значением |
| источник | вычисляется из данных службы или вводится по подразделениям |
| служба-владелец | вводить значения могут пользователи с уровнем «ввод данных» к ней (в своей области структуры) |
| где ожидается значение | типы уровней структуры; пусто — где есть значения |
| порядок, активен | — |

**Вычисляемые показатели** (источники описаны в коде, `INDICATOR_SOURCES`):
- персонал: принято и уволено за месяц — по подразделению записи реестра, сопоставленному с подразделением структуры по названию или коду; текучесть и время закрытия позиции — уровня компании;
- техподдержка: заявки в работе на конец месяца, решено за месяц, отношение решено/получено — к подразделению службы;
- партнёрства: доля партнёрств «в норме» — к подразделению службы.

Подразделение службы задаётся настройкой «служба → подразделение структуры» (по умолчанию — по кодам HR, TECH, PROJ).

**Вводимые показатели** — значение, цель и комментарий за месяц по подразделению; ввод формой или загрузкой Excel (проверка → план → применение, как в 0.2.0). Так приходят финансовые показатели (выручка, затраты, ФОТ, исполнение бюджета) и операционные (выполнение плана работ, удовлетворённость клиентов).

### Значение, статус и свёртка

- Значение показателя у подразделения за период — собственное (введённое или вычисленное), а если его нет — свёртка значений дочерних подразделений (сумма или среднее). Источник значения виден: «введено», «из данных службы», «сумма по N подразделениям».
- Статус показателя — светофор по правилу: зелёный · жёлтый · красный · нет оценки.
- **Пропуск данных** (решение владельца продукта в 0.2.0): если значение ожидается (тип уровня из «где ожидается»), а его нет — статус «Нет данных», а сам пропуск отмечается как **критичное нарушение полноты** и перечисляется отдельно.
- **Статус подразделения** — худший из статусов его показателей и статусов дочерних подразделений. «Нет данных» статус не ухудшает, но учитывается в нарушениях полноты.
- **Объяснение статуса** — список показателей и подразделений, которые его определили: «Красный: Текучесть кадров в «Коммерческая служба» — 14 % при цели 8 %».
- **Ручной статус** (заметка руководителя): руководитель подразделения (или `reports.manage`) может отметить подразделение за период — «под контролем» с комментарием. Расчётный статус не меняется, заметка показывается рядом с ним.

### Доступ (ADR-0009)

- **Область**: вершины отчёта — вершины области пользователя (вся компания — корни структуры; ветка или подразделение — основное, руководимые и дополнительные подразделения).
- **Глубина детализации** `drill_depth`: видны вершины и `drill_depth` уровней под ними (без ограничения — вся ветка). Подразделения глубже в ответе не перечисляются: их значения входят в свёртку видимых уровней, а у последнего видимого уровня отмечено «детализация недоступна».
- **Классы данных**: показатели недоступного класса не возвращаются вовсе — ни значения, ни статуса, ни упоминания в объяснении. Статус подразделения пользователь видит **по доступным ему показателям** (так влияние денежных показателей не раскрывается через цвет); интерфейс пишет «статус по N доступным показателям».
- **Исходные данные**: ссылка из показателя на дашборд службы — при доступе к службе; на реестр — при праве на исходные записи.
- **Выгрузка** (Excel, PDF отчёта) — при праве на выгрузку.

### Хранение (миграция 0015)

- `indicators` — каталог (поля выше);
- `indicator_values` — `indicator_id`, `department_id`, `period` (первое число месяца), `value`, `target`, `comment`, `source` (`manual` · `import`), `updated_by_id`, `updated_at`; уникальность (показатель, подразделение, период). Вычисляемые показатели не хранятся — считаются из данных служб;
- `unit_status_notes` — `department_id`, `period`, `status` (`watch` — «под контролем»), `comment`, `author_id`, `created_at`;
- настройка `report_service_units` (app_settings) — подразделения служб.

Расчёт отчёта за период — один проход по снимку структуры и значениям периода; результат кэшируется в памяти процесса по (период, ревизии структуры, ревизии данных служб, ревизии значений показателей) и затем фильтруется под права пользователя без пересчёта.

### API

- `GET /api/reports/scorecard?period=YYYY-MM&root=<id>` — вершины области (или выбранный видимый уровень) с видимыми уровнями до предела глубины: статус, нарушения полноты, показатели (значение, цель, статус, источник, изменение к прошлому периоду), объяснение, признак «детализация недоступна», заметка; плюс сведения о доступе (`scope`, `drill_depth`, скрытые классы данных — только их названия).
- `GET /api/reports/units/{id}?period=` — подразделение: показатели с трендом за 12 месяцев, дочерние подразделения со статусами, объяснение, ссылки на дашборды служб.
- `GET /api/reports/periods` — периоды с данными.
- `GET/POST/PATCH/DELETE /api/reports/indicators` — каталог (`reports.manage`); чтение каталога — доступных классов, любому пользователю.
- `GET /api/reports/values?period=&indicator=` и `PUT /api/reports/values` — ввод (служба-владелец, уровень «ввод данных», в своей области); `POST /api/reports/values/import` — загрузка Excel/CSV (план → применение).
- `PUT /api/reports/units/{id}/note` — заметка о статусе.
- `GET /api/pdf/reports/scorecard?period=&root=` — PDF отчёта (право на выгрузку).

### Интерфейс

- «Сквозной отчёт» (`/reports`): период; сводка вершины области (статус, нарушения, объяснение); **матрица** «подразделения × показатели» с цветом ячеек и раскрытием уровней в пределах глубины; **оргсхема статусов** (карточки структуры, окрашенные статусом); панель подразделения с трендами и переходом к дашбордам служб; строка «Ваш доступ: …».
- «Ввод показателей» (`/reports/entry`): таблица подразделения × показатели за месяц, загрузка Excel.
- «Показатели» (`/admin/indicators`): каталог, правила, классы, свёртка; настройка подразделений служб.
- «Обзор»: карточка статуса области пользователя.

## Последствия

- Отчёт одинаково работает для первого лица и рядового сотрудника — различаются только область, глубина и классы данных из профиля и личных настроек.
- Веса показателей в статусе и закрытие периода (фиксация значений) — следующий шаг: модель допускает их добавление без изменения API.
