# ADR-0012. Проектный офис: сырьё Jira и GitLab, производственный календарь

- Статус: принято (концепция 0.6.0; реализация по этапам)
- Дата: 2026-11-21
- Версия: 0.6.0 (план)
- Связано: ADR-0011 (интеграции, секреты, журнал запусков), ADR-0010 (сквозные отчёты), ADR-0007 (структура компании); план [v0.6.0-project-office](../plans/v0.6.0-project-office.md)

## Контекст

Проектному офису и офису разработки нужны статистики по рабочим часам, проектам и коду. Источники —
собственные системы компании (проверено 2026-11-21, read-only пробы с сервера):

| Система | Адрес | Что подтверждено пробами |
| --- | --- | --- |
| Jira | `https://jira.almi-partner.ru:8443` | **Server 8.3.5** (не Cloud): `POST /rest/api/2/search` со пагинацией `startAt`; поля `worklog` (расширенный), `timespent`, `assignee`; basic-авторизация учётной записью; проекты читаются |
| Confluence | `https://confluence.almi-partner.ru` | REST `/rest/api/space` отвечает той же учётной записью; публикация отчётов уже есть (ADR-0011) |
| GitLab | `https://gitlab.almi-partner.ru` | self-managed, API **v4**: `/api/v4/projects` частично доступен без токена, остальное — токен `read_api` (будет выдан) |

Существующий коннектор Jira (ADR-0011) собирает **агрегаты по JQL** сразу в значения показателей —
сырых данных нет, drill-down до задачи невозможен. Коннектора GitLab нет. Владелец продукта
зафиксировал: доступ **строго read-only**, креды — **только в секретах** (шифрование ADR-0011),
сопоставление людей — по одинаковым логинам/почтам, план часов — из **производственного календаря**.

## Решение

### 1. Два уровня данных: агрегаты (как сейчас) и сырьё (новое)

Коннектор Jira сохраняет режим «JQL → показатели» без изменений. Добавляется **сырьё** — таблицы
для drill-down и аналитики; расчёт показателей идёт из сырья, а не из Jira на лету:

| Таблица | Что хранит | Перезаливка/окно |
| --- | --- | --- |
| `jira_projects` | ключ, название, ведущий, состояние | полное обновление (кнопка/расписание) |
| `jira_issues` | ключ, проект, тема, статус, тип, приоритет, assignee/reporter, created/resolved, labels, story points | окно 90 дней по `updated` + досоздание закрывшихся |
| `jira_worklogs` | автор, задача, дата, часы, комментарий | окно 180 дней по `started` (правки редки) |
| `gitlab_projects` | id, путь, имя, группа, архивность | полное обновление |
| `gitlab_commits_daily` | **агрегат** день × автор × проект: количество, добавленные/удалённые строки | инкремент с `since` (агрегат — сырьё компактно) |
| `gitlab_merge_requests` | id, проект, автор, название, даты создания/мерджа/закрытия, размер диффа, reviewers, длительность ревью, `jira_keys` (распарсенные из названия/ветки) | окно 1 год |

Сырьё не проходит конвейер «Входящих» (это не файлы): коннектор пишет в таблицы напрямую в
транзакции, журнал запусков (ADR-0011) показывает счётчики («задач: N, worklog-записей: M»).

### 2. Коннекторы

**Jira (расширение, `kind=jira`)** — новые действия рядом с существующими показателями:
- `projects` — `/rest/api/2/project?maxResults=100`;
- `issues` — `POST /rest/api/2/search`, JQL окна `updated >= -90d` (шаблон настраивается),
  `fields=[summary,status,assignee,reporter,created,resolved,timespent,labels,issuetype,priority]`,
  пагинация `startAt` по 100 (облачного `search/jql` в 8.3.5 нет — ветка Cloud остаётся для неё);
- `worklogs` — задачи из окна, `fields=worklog` (+дозапрос полной постраничной выгрузки worklog
  задачи при > 20 записей), строки `{author.key/email, started, timeSpentSeconds, comment}`.

**GitLab (новый, `kind=gitlab`)** — `url_field` (адрес инстанса), секрет `token` (`read_api`):
- `projects` — `GET /api/v4/projects?membership=true` / по группе из настроек, пагинация по `X-Next-Page`;
- `commits` — по каждому проекту `GET /projects/{id}/repository/commits?since=…&per_page=100`,
  свёртка в дневной агрегат по автору (email из commit);
- `merge_requests` — `GET /projects/{id}/merge_requests?updated_after=…`, детали ревью —
  `/merge_requests/{iid}/ approvals?reviewer_details` по мере доступности версии GitLab;
- `pipelines` — агрегат день × проект × статус (`GET /projects/{id}/pipelines?updated_after=…`).

Разрешённые узлы — `GITLAB_ALLOWED_HOSTS` (по образцу `JIRA_ALLOWED_HOSTS`). Все запросы —
только GET/POST-поиск (Jira `/search` — чтение): **никаких изменяющих вызовов** в коде коннекторов.

### 3. Сопоставление людей

Логины/почты совпадают во всех системах: `jira_worklogs.author.email` и email коммиттера GitLab
сопоставляются с `employees.email` (регистр не важен). Исключения (почта в системе отличается,
один человек — несколько учёток) — таблица `external_identities(service, external_email, employee_id)`,
поддерживается на экране службы. Несопоставленные авторы видны в реестре как «внешние» и в часы
проектного офиса не попадают, пока их не сопоставят.

### 4. Производственный календарь и план часов

- Встроенный календарь РФ (`app/services/production_calendar.py`): праздники и переносы по
  постановлениям Правительства на 2025–2027, функция `capacity(from, to) → часы` (рабочий день 8 ч,
  предпраздничный 7 ч). Корпоративные отличия — таблица `calendar_overrides(date, hours, note)`.
- Ёмкость человека на период = календарь минус отпуска (реестр отсутствует — заглушка: без вычета,
  отметить в «Ограничениях» до появления учёта отпусков).
- План по проектам — `project_hour_plans(project_key, month, hours, note)`: задаёт руководитель
  проекта в интерфейсе службы; план на человека не делится (достаточно проекта × месяца).
- Факт/план: факт — `jira_worklogs` × доля проекта; часы вне задач Jira (внутренние) видны
  отдельной строкой как «не привязано к проекту».

### 5. Служба «Проектный офис» и показатели

Registry-запись новой службы `project_office` (доступ — по профилям, как у существующих):
- дашборд: часы факт против плана по проектам и людям, lead time (created→resolved) p50/p90,
  WIP, доля просроченных, активность разработки (коммиты/MR по неделям), время ревью MR,
  успешность пайплайнов;
- реестры: задачи Jira (окно сырья) и мерж-реквесты — с фильтрами и выгрузкой;
- сквозной отчёт — показатели «часы к плану», «lead time», «доля просроченных» для подразделений
  офиса разработки через существующий каталог показателей.

### 6. Этапы 0.6.0

1. Коннектор GitLab + агрегаты + реестр MR (вертикаль: секреты → расписание → журнал → реестр).
2. Сырьё Jira (projects/issues/worklogs) + миграция `0017_project_office`.
3. Служба «Проектный офис»: календарь, планы часов, дашборд, показатели сквозного отчёта.
4. Почтовая подписка (вкл/выкл на пользователя) и лента изменений (семантика — план 0.5.0).

## Последствия

- Хранение сырья умеренное: worklogs и MR — тысячи строк в год, агрегат коммитов — сотни;
  окно перезаливки делает повторные запуски дешёвыми.
- Jira 8.3.5 (2019) — держать в уме: без облачных эндпоинтов, basic-auth (для Data Center новых
  версий токены появятся — коннектор уже различает типы).
- Секреты не покидают продукт (шифрование ADR-0011), в журнал попадают маскированные значения.
- Реестр отпусков для точной ёмкости — отдельное решение на будущее (сейчас календарь без вычета).
