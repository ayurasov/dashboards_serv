# Runbook: обновление до 0.3.0

Применимо к установкам версии 0.2.0 (схема `0014_org_access`). Установки 0.1.0 и более ранние сначала проверяются по `upgrade-to-0.2.0.md` (и `upgrade-to-0.1.0.md`) — миграции до 0015 выполнятся за один старт.

Что меняется — «Руководство по развёртыванию», раздел «Обновление до 0.3.0»; решение — ADR-0010 (сквозные отчёты). Миграция `0015_reports` только добавляет таблицы (`indicators`, `indicator_values`, `unit_status_notes`, `report_revision`), существующие данные и доступ пользователей не меняет и поддерживает откат. Новых переменных окружения нет — настраивать ничего не нужно.

## Перед обновлением

1. Объявите окно обслуживания (5–10 минут); приложение перезапускается один раз.
2. Убедитесь, что установлена 0.2.0 и схема актуальна:
   ```bash
   curl -s http://127.0.0.1:8000/api/health        # "version": "0.2.0", schema.current == "0014_org_access"
   ```
3. Сохраните копию базы и проверьте, что файл не пустой:
   ```bash
   docker compose exec -T db pg_dump -U dashboards -d dashboards -Fc > before-0.3.0.dump
   ls -lh before-0.3.0.dump
   ```
   SQLite — через API резервного копирования (см. `backup-restore.md`).
4. Запишите контрольные числа:
   ```bash
   docker compose exec -T db psql -U dashboards -d dashboards -c "
     SELECT (SELECT count(*) FROM users) AS users,
            (SELECT count(*) FROM users WHERE is_active) AS active,
            (SELECT count(*) FROM departments) AS departments,
            (SELECT count(*) FROM service_access) AS service_access,
            (SELECT count(*) FROM access_profiles) AS profiles;"
   ```
5. Если в `docker-compose.override.yml` или `.env` закреплён тег образа (`APP_VERSION=0.2.0`), уберите его или задайте `0.3.0`.

## Обновление

```bash
git fetch && git checkout v0.3.0
docker compose up -d --build
docker compose logs app | grep -E "Схема базы|ERROR"
```

В журнале — `Схема базы обновлена: 0014_org_access → 0015_reports`.

## Проверка

1. `curl -s http://127.0.0.1:8000/api/health` → `"status": "ok"`, `"version": "0.3.0"`, `schema.current == schema.head == "0015_reports"`.
2. Контрольные числа после обновления:
   ```bash
   docker compose exec -T db psql -U dashboards -d dashboards -c "
     SELECT (SELECT count(*) FROM users) AS users,                       -- как до обновления
            (SELECT count(*) FROM users WHERE is_active) AS active,      -- как до обновления
            (SELECT count(*) FROM departments) AS departments,           -- как до обновления
            (SELECT count(*) FROM service_access) AS service_access,     -- как до обновления
            (SELECT count(*) FROM access_profiles) AS profiles,          -- как до обновления
            (SELECT count(*) FROM indicators) AS indicators,             -- 8: вычисляемые показатели служб
            (SELECT count(*) FROM indicator_values) AS indicator_values, -- 0
            (SELECT count(*) FROM unit_status_notes) AS notes,           -- 0
            (SELECT count(*) FROM report_revision) AS report_revision;   -- 1"
   ```
3. Войдите администратором: в меню — «Сквозной отчёт» с показателями из данных служб, в «Администрировании» — «Показатели» с восемью вычисляемыми показателями; в карточке любого пользователя на вкладке «Полномочия» — три полномочия, «Ведёт сквозные отчёты» ни у кого не отмечено.
4. «Показатели» → блок «Подразделения служб»: у техподдержки, партнёрств и службы персонала найдено подразделение (по кодам TECH, PROJ, HR). Если «Подразделение не найдено», выберите подразделение службы и сохраните.
5. Откройте «Обзор», «Структуру компании», дашборды трёх служб и PDF-отчёт любой страницы — работают как в 0.2.0.

## После обновления

1. Заполните каталог показателей («Руководство администратора», раздел «Показатели и сквозной отчёт»): вычисляемые из данных служб (заявки в работе, решённые заявки, текучесть, доля партнёрств «в норме»…) и вводимые по подразделениям — финансовые и операционные, с правилами светофора, свёрткой и типами уровней, где значения обязательны. Добавьте первый вычисляемый показатель, например «Заявки в работе», и убедитесь, что он появился в «Сквозном отчёте».
2. Выдайте уровень «Ввод данных» к службам-владельцам тем, кто вводит значения (например, «Финансовая служба — Ввод данных» финансовым контролёрам), и полномочие «Ведёт сквозные отчёты» тому, кто ведёт каталог.
3. Проверьте профили доступа: глубина детализации и классы данных начинают действовать в сквозном отчёте. Войдите (или попросите войти) сотрудниками разных уровней — первым лицом, руководителем направления, руководителем службы, рядовым сотрудником — и сверьте строку «Ваш доступ: …» и состав отчёта с ожиданиями («Руководство администратора», раздел «Настройка уровней сотрудников»).
4. Убедитесь, что у сотрудников указаны подразделения: без них при области «Своя ветка» или «Своё подразделение» отчёт пуст («Область отчёта пуста»).
5. Сообщите сотрудникам о новом разделе: «Руководство пользователя», разделы «Сквозной отчёт» и «Ввод показателей»; в приложении — «Что нового».

## Откат

Откат миграции 0015 сам снимает полномочие «Ведёт сквозные отчёты» у пользователей (в 0.2.0 его нет). Проверить после отката, что его ни у кого не осталось:

```bash
docker compose exec -T db psql -U dashboards -d dashboards -c "SELECT username FROM users WHERE capabilities::text LIKE '%reports.manage%';"
```

Предпочтительно — восстановить копию и вернуть 0.2.0:

```bash
docker compose stop app
docker compose exec -T db pg_restore -U dashboards -d dashboards --clean --if-exists < before-0.3.0.dump
git checkout v0.2.0 && docker compose up -d --build
curl -s http://127.0.0.1:8000/api/health        # "version": "0.2.0"
```

Если после обновления внесены данные служб, которые нужно сохранить, откатите схему образом 0.3.0, затем верните 0.2.0:

```bash
docker compose stop app
docker compose run --rm --no-deps -w /app/backend --entrypoint alembic app downgrade 0014_org_access
git checkout v0.2.0 && docker compose up -d --build
```

При откате схемы теряются каталог показателей, введённые значения, цели и комментарии, заметки «под контролем» и настройка «Подразделения служб». Пользователи, структура, доступ и данные служб не затрагиваются; повторно входить не нужно.
