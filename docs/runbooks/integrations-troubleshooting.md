# Runbook: неполадки интеграций и входящих данных

Применимо к версии 0.4.0 и новее. Устройство — ADR-0011; настройка — «Руководство администратора», раздел «Интеграции и входящие данные»; сервер — «Руководство по развёртыванию», раздел «Входящие данные и интеграции».

Команды выполняются из каталога установки (`/opt/dashboards_serv`). Где искать:

| Что | Где |
| --- | --- |
| Состояние подключения, последняя ошибка, итог последнего запуска | **Администрирование → Интеграции**, карточка подключения |
| Подробный итог каждого запуска | карточка → **Журнал запусков** (столбцы «Итог» и «Сводка») |
| Текст проверки с подсказкой и подробностями | карточка → **Проверить** (сохранённые настройки) или **Настроить → Проверить** (введённые значения) |
| Папка «Входящие» и планировщик | **Входящие данные → Папка** |
| Что стало с файлом | **Входящие данные → Элементы**, карточка элемента; для файла из папки — `<имя>.result.json` рядом с файлом в `processed/` или `rejected/` |
| Кто и когда проверял, запускал, менял подключения и ключи | **Журнал изменений**, объекты «Подключение», «Ключ входящих вызовов», «Элемент входящих» |
| Журнал сервера | `docker compose logs app`, `docker compose logs worker` (секреты в нём заменены на «…») |

```bash
docker compose ps                                                          # app — healthy, worker — Up
docker compose exec -T -w /app/backend app python -m app.cli integrations list   # номер, вид, название, включено, расписание, состояние
```

## Проверка подключения не проходит

1. Прочитайте сообщение проверки и подсказку под ним. Подробности (версия системы, пользователь или ключ и его области, доступные списки и направления) — в блоке «Подробности».
2. По сообщению:

   | Сообщение | Что сделать |
   | --- | --- |
   | «Не удалось подключиться к …: проверьте адрес и доступность сети» | проверьте доступ из контейнера (ниже) — межсетевой экран, маршрут, DNS, `HTTPS_PROXY` / `NO_PROXY` |
   | «Не удалось подключиться к … через прокси http://…:3128 (HTTPS_PROXY / HTTP_PROXY; если узел доступен напрямую, добавьте его в NO_PROXY)…» | запрос ушёл через прокси — раздел «Прокси и NO_PROXY» ниже |
   | «Превышено время ожидания подключения к …», «… не ответил за 30 с» | система недоступна или перегружена; при работе через прокси — проверьте, что узел не в `NO_PROXY` по ошибке |
   | «Ошибка TLS-сертификата …» | корпоративный или самоподписанный сертификат: выключите «Проверять сертификат» в настройках подключения |
   | «… перенаправляет запрос (30x) на …» | укажите в подключении итоговый адрес — тот, на который перенаправляет система (обычно с `https://` или с путём, например `/jira`, `/wiki`) |
   | «… вернул неожиданный ответ — проверьте адрес; возможно, отвечает страница входа или прокси» | адрес ведёт на страницу входа SSO, на прокси или на другую систему: откройте адрес API в браузере с сервера |
   | «… отклонила учётные данные подключения (401)», «Jira отклонила логин или токен (401)…» | неверный логин, токен истёк или выбран не тот «Тип подключения» (Cloud / Server) — **Настроить**, введите токен заново |
   | «Недостаточно прав в … (403)» | права учётной записи в системе — «Руководство администратора», раздел о системе, абзац «Права в …» |
   | «… требует ввести CAPTCHA для этой учётной записи…» | войдите в Jira или Confluence браузером под этой учётной записью и пройдите проверку |
   | «Подключено …, но не хватает: …», «Ключ «…» принят в «По Делу» …, но не хватает: …» («По Делу»), «… в запросах ошибки: …» (1С) | вход выполнен или ключ принят, но нет полномочия, области ключа, доступа к списку или набора в OData — выдайте права или исправьте настройку |
   | сообщения о ключе интеграции «По Делу» или «Пульса» | раздел «Ключ «По Делу» или «Пульса» не принят» ниже |

3. Проверьте доступ из контейнера — так же, как ходит приложение (с теми же прокси-переменными):

   ```bash
   docker compose exec app python -c "import urllib.request as u; print(u.urlopen('https://jira.company.ru/rest/api/2/serverInfo', timeout=5).status)"
   docker compose exec app sh -c 'echo HTTP_PROXY=$HTTP_PROXY HTTPS_PROXY=$HTTPS_PROXY NO_PROXY=$NO_PROXY'
   ```

   Ошибка соединения здесь — вопрос сети, а не настроек подключения. Проверьте и `worker`: `docker compose exec worker …` — запуски по расписанию идут из него.
4. Исправив, нажмите **Проверить** на карточке: успешная проверка сохранённых настроек отмечает подключение проверенным, после этого его можно включить.

## Узел не разрешён

Сообщение: «Подключение к jira.example.com запрещено настройками сервера (JIRA_ALLOWED_HOSTS)». Адрес не сохраняется и не проверяется, у поля адреса — подсказка с именем переменной.

1. Посмотрите текущее значение:
   ```bash
   docker compose exec app sh -c 'echo $JIRA_ALLOWED_HOSTS'
   ```
2. Если адрес верный, добавьте узел в `.env` (или в override для `app` и `worker`) — через запятую; `.company.ru` разрешает домен и все поддомены:
   ```bash
   JIRA_ALLOWED_HOSTS=jira.company.ru,.atlassian.net
   ```
3. Примените: `docker compose up -d` (перезапустятся `app` и `worker`) и повторите проверку.

Для почтового ящика переменная одна на все способы: `EXCHANGE_ALLOWED_HOSTS` должна разрешать сервер EWS или IMAP, а для Microsoft 365 — `login.microsoftonline.com` и `graph.microsoft.com`. Если адрес неверный — исправьте адрес, а не расширяйте список: список нужен, чтобы запросы сервера с секретами не уходили на произвольные узлы.

## Секреты не расшифровываются

Признаки: карточка подключения — «Секрет нужно ввести заново» с текстом «Сохранённый секрет не удаётся расшифровать (сменился SECRET_KEY сервера) — введите его заново»; проверка и запуски завершаются ошибкой; `integrations list` показывает «ошибка: …». Другой текст — «Секрет введён для адреса …, а подключение настроено на … — введите токен или пароль заново» — означает, что изменился адрес подключения.

Причины:

- изменён `SECRET_KEY` в `.env` (или задан другой при переносе на новый сервер);
- база восстановлена из копии на сервере с другим `SECRET_KEY`;
- запись подключения изменена в базе вручную (секрет привязан к подключению и адресу).

Что сделать:

1. Если ключ сменили по ошибке и прежнее значение известно — верните его в `.env` и выполните `docker compose up -d`: секреты снова расшифруются, вводить их не нужно.
2. Иначе — для каждого подключения из `integrations list` с ошибкой: **Интеграции → Настроить**, введите пароль, токен, вебхук или секрет приложения заново (в форме — «Сохранённый секрет не подходит»), **Проверить**, **Сохранить**. Включённое подключение после ввода нужно проверить снова.
3. Ключи для входящих вызовов от `SECRET_KEY` не зависят: они хранятся как отпечатки SHA-256 и продолжают работать.

## Планировщик не работает

Признаки: **Входящие данные → Папка**, блок «Планировщик» — «Не запущен» или «Не отвечает»; файлы лежат в папке; подключения не запускаются по расписанию (на карточке «следующий запуск» в прошлом, «Последний запуск» не меняется).

1. Состояние и журнал сервиса:
   ```bash
   docker compose ps worker
   docker compose logs --tail 100 worker
   ```
2. По журналу:

   | Что видно | Причина и решение |
   | --- | --- |
   | сервиса `worker` нет в `docker compose ps` | старый или свой compose-файл без планировщика — добавьте сервис из `docker-compose.yml` 0.4.0, `docker compose up -d` |
   | `Exited`, в журнале ошибка подключения к базе | неверный `DATABASE_URL` у планировщика — он должен получать те же переменные, что `app` |
   | «Планировщик ждёт актуальную схему базы (… → …): миграции выполняет сервис app» | приложение не применило миграции или работает старая версия: проверьте `docker compose logs app`, `/api/health` |
   | «Планировщик: ошибка разбора папки «Входящие»», «ошибка запусков по расписанию» с трассировкой | ошибка в программе или в данных: сохраните журнал и передайте разработчикам; такт продолжается |
   | «Планировщик: не удалось записать отметку о работе» | база недоступна или перегружена — отметка «Не отвечает» при живом процессе |

3. Перезапуск и один такт вручную:
   ```bash
   docker compose restart worker
   docker compose exec -T -w /app/backend worker python -m app.cli worker --once
   ```
   После такта отметка на странице «Папка» обновится («Работает», «последняя отметка … назад»).
4. Отметка «Не отвечает» при нескольких экземплярах показывает время последнего такта любого из них; если один экземпляр остановлен, остальные продолжают работу.

## Файлы застряли в папке

Признаки: файлы лежат в корне или подпапках папки «Входящие», «Ждут разбора» не уменьшается.

1. **Входящие данные → Папка → Проверить сейчас**: итог покажет, сколько файлов взято, сколько «дописываются» и замечания (например, «ссылка за пределы папки «Входящие» — не открывается»). Если «Проверить сейчас» забирает файлы, а сами они не забираются — не работает планировщик (раздел выше).
2. Проверьте, почему файл не берётся:

   | Причина | Как понять | Что сделать |
   | --- | --- | --- |
   | файл ещё меняется | его время изменения моложе `INBOX_SETTLE_SECONDS` (10 с); в итоге — «дописываются» | дождитесь окончания записи; выгружайте во временное имя (`*.tmp`) и переименовывайте в конце |
   | скрытое или временное имя | `.имя`, `~$имя`, `*.tmp`, `*.part`, `*.partial`, `*.crdownload`, `*.swp`, `*~`, `*.result.json` | переименуйте файл |
   | подпапка с другим именем | например, `Выгрузки/` или `tp_weekly/` вместо `tp-weekly/` | только подпапки с ключом набора и корень; перенесите файл |
   | символьная ссылка | `ls -l` показывает `->` | положите сам файл |
   | нет прав | состояние папки «Только чтение» | права на каталог для пользователя контейнера (`docker compose exec app id`) — «Руководство по развёртыванию», раздел «Папка «Входящие»» |
   | папка не та | путь на странице «Папка» не совпадает с каталогом, куда пишет 1С | исправьте `INBOX_DIR` или монтирование тома для `app` и `worker` |

3. Файлы в `.work/` — в обработке. Файл, пролежавший там дольше часа (процесс остановили посреди разбора), возвращается на место при следующем разборе.
4. Файл забран, но не применён — это не «застрял»: смотрите элемент на вкладке «Элементы» и отчёт `*.result.json` в `processed/ГГГГ-ММ/` (ожидает подтверждения, нераспознан) или в `rejected/` (ошибка, повтор, слишком большой). Применение без подтверждения включается правилом «применять сразу» для папки и набора.

```bash
docker compose exec app sh -c 'ls -la /data/inbox /data/inbox/tp-weekly; ls /data/inbox/rejected | tail'
docker compose exec app sh -c 'cat "/data/inbox/rejected/<имя файла>.result.json"'
```

## Ключ «По Делу» или «Пульса» не принят

Подключения «По Делу» (1.4.5 и новее) и «Пульса проекта» (0.6.0 и новее) по умолчанию работают по ключу интеграции, который выпускает администратор этой системы: в «По Делу» — «Настройки → Интеграции → Ключи интеграций», в «Пульсе» — «Интеграции → Ключи доступа». Ключ — секрет подключения: в журналах он заменён на «…».

| Сообщение | Причина | Что сделать |
| --- | --- | --- |
| ««По Делу» не приняла ключ интеграции (401): …» (то же для «Пульс проекта») | ключ введён с ошибкой, перевыпущен в системе-партнёре или выпущен для другого стенда | попросите действующий ключ (или выпустите заново) и введите его: **Настроить → Ключ интеграции → Заменить** |
| «Ключ интеграции отозван администратором «По Делу» — выпустите ключ заново: …» | ключ отозван в «По Делу» | в «По Делу» — **Выпустить снова** (или новый ключ для системы «Дашборды»), введите новый ключ в подключении |
| «У ключа нет доступа «…» (область …) — добавьте её ключу: …», «У ключа «…» нет областей: …», «У ключа «…» нет права «Проекты и планы» (projects.read) — добавьте его ключу: …» | у ключа нет области (права), нужной действию | добавьте область в системе-партнёре — ключ останется прежним, новые права действуют со следующего запроса; затем **Проверить** |
| «… Не хватает: область «Комментарии к задачам» (tasks.comment) — для «Отмечать задачу комментарием» …» (проверка прошла) | ключ работает, но не для всех возможностей | добавьте область или выключите возможность в настройках подключения |
| «Ключ «…» превысил лимит частоты запросов «По Делу» (429) — повторите позже» (то же для «Пульс проекта») | больше 120 запросов в минуту на ключ — частые запуски, проверки подряд или тот же ключ введён в двух подключениях | подождите минуту; «Забрать данные из задач» продолжит с места остановки сам. Разнесите расписания по времени; не вводите один ключ в несколько подключений и стендов |
| «Ключ интеграции «По Делу» начинается с podelu_ — проверьте ключ», «Ключ интеграции «Пульса» начинается с puls_ — проверьте ключ» | в поле введён ключ другой системы — например, ключ «Пульса» в подключении «По Делу» или ключ `dash_…` «Дашбордов» | введите ключ, выпущенный нужной системой |
| «По адресу подключения нет API ключей интеграций «По Делу» (/api/integrations/v1/ping, 404): «По Делу» старше 1.4.5 или адрес указан неверно…» (у «Пульса» — `/api/integration/v1/ping` и 0.6.0) | у системы нет API ключей: версия старше, адрес ведёт не туда (не тот путь, другой стенд) | проверьте адрес и версию (ниже); для старой версии выберите режим «Служебная учётная запись (для версий до …)» |
| ««Пульс проекта» 0.5.… не сообщает права ключа — это версия до 0.6.0, где ключ интеграции один и выдан «По Делу»…» | «Пульс» 0.5: ключ интеграции один и принадлежит «По Делу» | обновите «Пульс» до 0.6.0 или выберите служебную учётную запись |
| «Ключ принят, но по адресу подключения отвечает не «По Делу» (app: …) — проверьте адрес» | адрес ведёт в другую систему с таким же API (например, в «Пульс») | исправьте адрес подключения |

Есть ли у системы API ключей — с сервера, теми же прокси-переменными, что у приложения:

```bash
docker compose exec app python -c "import requests; print(requests.get('https://podelu.company.ru/api/integrations/v1/ping', timeout=5).status_code)"
docker compose exec app python -c "import requests; print(requests.get('https://puls.company.ru/api/integration/v1/ping', timeout=5).status_code)"
# 401 — API есть, нужен ключ; 404 — версия старше 1.4.5 («По Делу») или 0.6.0 («Пульс») либо неверный адрес
```

Ключ с ограниченными областями — нормальная настройка: например, ключ только с «Задачами и вложениями» и «Комментариями к задачам» для подключения, которое забирает файлы. Проверка «По Делу» проходит, если работает хотя бы одно действие, и перечисляет, чего не хватает остальным. У «Пульса» без права «Показатели проектов» (`projects.stats`) показатель `puls.blocked` не обновляется, а направления сопоставляются только по названию — запуск с id направлений в сопоставлении завершается «Частично».

## Запуск прерван

Признаки: в журнале запусков итог «Запуск прерван» — «Запуск прерван: процесс приложения или планировщика остановился до окончания запуска (перезапуск, сбой) — подключение можно запустить снова»; на карточке под последним запуском — «Процесс остановился до окончания запуска (перезапуск или сбой) — подключение можно запустить снова.»; в журнале планировщика — «Планировщик: прерванных запусков подключений — N (отмечены в журнале)».

Запуск, который идёт дольше двух часов, считается прерванным: процесс, выполнявший его, остановлен (`docker compose restart`, обновление, нехватка памяти, сбой сервера). Пока два часа не прошли, карточка показывает «Выполняется запуск с … — дождитесь окончания», и новый запуск не начинается.

1. Посмотрите, что остановило процесс: `docker compose logs --since 3h app worker | grep -iE "error|killed|SIGTERM|Планировщик"`, `docker compose ps` (перезапуски), `dmesg | grep -i oom` на сервере.
2. Запустите действие снова — **Запустить** на карточке или дождитесь расписания. Данные, которые прерванный запуск успел записать, остаются; уже забранные файлы повторно не скачиваются.
3. Если запуски прерываются постоянно на одном действии — оно не укладывается в время до перезапуска процесса: например, «Забрать данные из задач» с тысячами файлов. Запустите его вручную несколько раз подряд (курсор сохраняется после каждой задачи) и сократите интервал расписания.

## Прокси и NO_PROXY

Признаки: «Не удалось подключиться к … через прокси http://proxy…:3128 (HTTPS_PROXY / HTTP_PROXY; если узел доступен напрямую, добавьте его в NO_PROXY)…» или «Превышено время ожидания подключения к … через прокси …»; внутренние системы недоступны, облачные — работают.

`docker-compose.yml` передаёт `HTTP_PROXY`, `HTTPS_PROXY` и `NO_PROXY` из `.env` в `app` и `worker`. Запрос к `https://` идёт через `HTTPS_PROXY`, к `http://` — через `HTTP_PROXY`, к узлам из `NO_PROXY` — напрямую.

1. Посмотрите переменные в обоих контейнерах:
   ```bash
   docker compose exec app sh -c 'echo HTTP_PROXY=$HTTP_PROXY HTTPS_PROXY=$HTTPS_PROXY NO_PROXY=$NO_PROXY'
   docker compose exec worker sh -c 'echo NO_PROXY=$NO_PROXY'
   ```
2. Добавьте внутренние системы в `NO_PROXY` в `.env` — через запятую. Понимаются: узел (`podelu.company.local` — он и поддомены), домен (`.company.local` или `*.company.local`), узел или IP-адрес с портом (`podelu.company.local:5000`, `10.0.0.5:8080` — только этот порт), сеть (`10.0.0.0/8`), `*` — все узлы.
   ```bash
   NO_PROXY=localhost,127.0.0.1,.company.local,10.0.0.0/8
   ```
3. Примените: `docker compose up -d` (перезапустятся `app` и `worker`) и нажмите **Проверить** на карточке.

Почтовый ящик по IMAP прокси не использует: соединение с почтовым сервером всегда прямое (подсказка у поля «Сервер IMAP»), поэтому порт IMAP (993 или 143) должен быть открыт с сервера «Дашбордов». EWS и Microsoft Graph идут через прокси, как остальные подключения.

## Ключ возвращает 401 или 429

Ответы `/api/inbound/v1` — JSON с `code`:

| Ответ | `code` | Причина | Что сделать |
| --- | --- | --- | --- |
| 401 | `auth_required` | нет заголовка `Authorization: Bearer dash_…` или он без слова `Bearer` | проверьте заголовок в 1С или скрипте; прокси не должен убирать `Authorization` |
| 401 | `invalid_key` | «Ключ недействителен или отозван»: опечатка, ключ отозван или выпущен заново (прежнее значение перестаёт работать сразу) | «Ключи для входящих вызовов»: состояние ключа и время «Выпущен»; при необходимости — **Выпустить заново** и обновите значение у отправителя |
| 403 | `scope_forbidden` | «Области ключа «…» не хватает: status» — запрос статуса ключом только с «Приёмом файлов» | выпустите ключ с нужными областями (области существующего ключа не меняются) |
| 429 | `rate_limited` | больше `INBOUND_RATE_LIMIT` запросов в минуту на ключ (120); счёт общий для всех процессов сервера — окно хранится в базе у ключа | выдержите паузу из заголовка `Retry-After` (секунд до конца окна); отправляйте файлы пачкой реже; при необходимости увеличьте `INBOUND_RATE_LIMIT` |
| 413 | `payload_too_large` | файл больше `INBOX_MAX_MB` | разделите выгрузку или увеличьте `INBOX_MAX_MB` и `client_max_body_size` прокси |

Проверка ключа с сервера:

```bash
curl -s https://dashboards.company.ru/api/inbound/v1/ping -H "Authorization: Bearer dash_…"
# {"ok":true,"app":"dashboards","name":"Дашборды компании","version":"0.4.0","key":{"name":"1С: ЗУП","prefix":"dash_…","scopes":["files"]},…}
```

Значение ключа система не хранит — восстановить его нельзя, только выпустить заново. Последний вызов каждого ключа виден в таблице ключей («Последний вызов», обновляется не чаще раза в минуту), файлы ключа — в списке «Входящих» с фильтром «Приём по API».

## Лимит входов «По Делу»

Признак: проверка или запуск подключения «По Делу» в режиме служебной учётной записи — «… ограничила число запросов (429): много попыток входа — подождите несколько минут и повторите». В режиме ключа входов нет — там свой предел, 120 запросов в минуту на ключ (раздел «Ключ «По Делу» или «Пульса» не принят»). Если «По Делу» уже 1.4.5 и новее, лучше перевести подключение на ключ.

«По Делу» допускает с одного адреса 10 входов в минуту и 50 в час. Подключение входит служебной учётной записью при каждой проверке и каждом запуске действия (и всегда выходит), поэтому лимит исчерпывают:

- частые проверки подряд при настройке;
- расписание обоих действий с маленьким интервалом (каждые 5 минут — уже 24 входа в час);
- несколько подключений «По Делу» или другие системы (например, «Пульс проекта» со своей синхронизацией), которые входят с того же адреса — для «По Делу» все они приходят с адреса сервера или прокси.

Что сделать:

1. Подождите: минутный лимит снимается через минуту, часовой — в течение часа. Не нажимайте «Проверить» повторно — каждая попытка тоже вход.
2. Увеличьте интервалы: «Синхронизировать структуру» — раз в сутки, «Забрать данные из задач» — каждые 15–30 минут.
3. Неверный пароль тоже расходует попытки: если перед 429 было «… отклонила вход: неверный логин или пароль служебной учётной записи», исправьте пароль.
4. Убедитесь, что служебная учётная запись не используется людьми или другими скриптами.

## Confluence отвечает 409

Признак: запуск «Опубликовать сквозной отчёт» — «Страницу «…» одновременно изменили в Confluence (версия устарела, 409) — опубликуйте отчёт ещё раз».

Подключение обновляет страницу с версией «текущая + 1». Если между чтением и записью страницу изменили (кто-то правил её вручную, работала вторая публикация в то же пространство), Confluence отвечает 409. Подключение один раз перечитывает страницу и повторяет запись; ошибка остаётся, только если страницу меняли и во время повтора.

1. Запустите публикацию ещё раз (**Запустить** у действия «Опубликовать сквозной отчёт»).
2. Проверьте, не публикуют ли в одну страницу два подключения или два стенда — у каждого должно быть своё пространство или своё «Название страницы».
3. Не правьте опубликованную страницу вручную: она обновляется автоматически, правки заменяются при следующей публикации (об этом написано во вступлении страницы). Свои материалы держите на соседней странице.
4. Если ошибка повторяется на каждом запуске, проверьте в истории страницы, кто её меняет: например, макрос или автоматизация Confluence, которые пересохраняют страницу.

Похожая ошибка при создании — «Страница «…» уже есть в пространстве …, но не найдена поиском (возможно, она в корзине)…»: восстановите или окончательно удалите страницу из корзины пространства либо измените «Название страницы».
