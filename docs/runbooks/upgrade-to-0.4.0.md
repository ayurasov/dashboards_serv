# Runbook: обновление до 0.4.0

Применимо к установкам версии 0.3.0 (схема `0015_reports`). Установки 0.2.0 и более ранние сначала проверяются по `upgrade-to-0.3.0.md` (и предыдущим регламентам) — миграции до 0016 выполнятся за один старт.

Что меняется — «Руководство по развёртыванию», раздел «Обновление до 0.4.0»; решение — ADR-0011 (интеграции и входящие данные). Миграция `0016_integrations` только добавляет таблицы (`integrations`, `integration_runs`, `inbound_keys`, `inbox_items`, `inbox_rules`), существующие данные и доступ пользователей не меняет и поддерживает откат. В `docker-compose.yml` появляются сервис `worker` (планировщик) и том `inbox` (папка «Входящие»); новые переменные окружения необязательны.

## Перед обновлением

1. Объявите окно обслуживания (10–15 минут); приложение перезапускается один раз, планировщик запускается впервые.
2. Убедитесь, что установлена 0.3.0 и схема актуальна:
   ```bash
   curl -s http://127.0.0.1:8000/api/health        # "version": "0.3.0", schema.current == "0015_reports"
   ```
3. Сохраните копию базы и проверьте, что файл не пустой:
   ```bash
   docker compose exec -T db pg_dump -U dashboards -d dashboards -Fc > before-0.4.0.dump
   ls -lh before-0.4.0.dump
   ```
   SQLite — через API резервного копирования (см. `backup-restore.md`).
4. Запишите контрольные числа:
   ```bash
   docker compose exec -T db psql -U dashboards -d dashboards -c "
     SELECT (SELECT count(*) FROM users) AS users,
            (SELECT count(*) FROM users WHERE is_active) AS active,
            (SELECT count(*) FROM departments) AS departments,
            (SELECT count(*) FROM indicators) AS indicators,
            (SELECT count(*) FROM indicator_values) AS indicator_values;"
   ```
5. **`SECRET_KEY` не меняйте.** С 0.4.0 им шифруются секреты подключений к системам компании; сохраните текущее значение из `.env` вместе с резервной копией.
6. Если в `docker-compose.override.yml` или `.env` закреплён тег образа (`APP_VERSION=0.3.0`), уберите его или задайте `0.4.0`. Если система запускается своим compose-файлом, перенесите в него сервис `worker` и том `inbox` из `docker-compose.yml` версии 0.4.0.
7. Если «Дашборды» будут подключаться к «По Делу» или «Пульсу проекта», заранее уточните их версии и попросите администраторов выпустить ключи интеграций для «Дашбордов» — подключение по ключу работает с «По Делу» 1.4.5 и новее и с «Пульсом» 0.6.0 и новее:
   - «По Делу»: «Настройки → Интеграции → Ключи интеграций» → **Выпустить ключ для системы** — название «Дашборды», код `dashboards`; области «Структура компании», «Сотрудники», «Задачи и вложения», «Комментарии к задачам» и списки задач, в которые кладут выгрузки;
   - «Пульс проекта»: «Интеграции → Ключи доступа» → **Выпустить ключ** — система «Дашборды компании», права «Проекты и планы» и «Показатели проектов».

   Ключ показывается один раз — пусть его передадут защищённым каналом тому, кто будет настраивать подключение. Для более ранних версий понадобится служебная учётная запись (её права — «Руководство администратора», разделы «По Делу» и «Пульс проекта»).
7. Если в override заданы переменные для сервиса `app` (вход по домену, синхронизация с AD), повторите их для `worker` — планировщик получает те же переменные.
8. Решите, где будет папка «Входящие»: именованный том `inbox` (по умолчанию) или каталог сервера, открытый по сети для 1С (раздел «Папка «Входящие»» руководства по развёртыванию). Для каталога сервера подготовьте его и права заранее.

## Обновление

```bash
git fetch && git checkout v0.4.0
docker compose up -d --build
docker compose logs app | grep -E "Схема базы|ERROR"
docker compose logs worker | grep -E "Планировщик|ERROR"
```

В журнале приложения — `Схема базы обновлена: 0015_reports → 0016_integrations`, в журнале планировщика — `Планировщик запущен: такт 30 с, папка «Входящие»: /data/inbox`. Сообщение `Планировщик ждёт актуальную схему базы` до старта приложения — норма: миграции выполняет только `app`.

## Проверка

1. `curl -s http://127.0.0.1:8000/api/health` → `"status": "ok"`, `"version": "0.4.0"`, `schema.current == schema.head == "0016_integrations"`.
2. `docker compose ps` — запущены `db`, `app` (healthy) и `worker` (Up; проверки здоровья у планировщика нет).
3. Контрольные числа после обновления:
   ```bash
   docker compose exec -T db psql -U dashboards -d dashboards -c "
     SELECT (SELECT count(*) FROM users) AS users,                        -- как до обновления
            (SELECT count(*) FROM users WHERE is_active) AS active,       -- как до обновления
            (SELECT count(*) FROM departments) AS departments,            -- как до обновления
            (SELECT count(*) FROM indicators) AS indicators,              -- как до обновления
            (SELECT count(*) FROM indicator_values) AS indicator_values,  -- как до обновления
            (SELECT count(*) FROM integrations) AS integrations,          -- 0
            (SELECT count(*) FROM inbox_items) AS inbox_items,            -- 0
            (SELECT count(*) FROM inbound_keys) AS inbound_keys,          -- 0
            (SELECT count(*) FROM inbox_rules) AS inbox_rules;            -- 0"
   ```
4. Войдите администратором: в меню — «Входящие данные» (страница «Входящих пока нет» с четырьмя способами), в «Администрировании» — «Интеграции» (вкладки «Подключения» и «Ключи для входящих вызовов») и «Вход по домену» по адресу `/admin/directory`; в карточке пользователя на вкладке «Полномочия» — пять полномочий, «Входящие данные» и «Интеграции» ни у кого не отмечены.
5. **Входящие данные → Папка**: состояние «Работает», «Папка есть — да», «Запись — разрешена»; блок «Планировщик» — «Работает» с отметкой не старше минуты.
6. Положите в папку тестовый файл и убедитесь, что он забран: например, выгрузку недельного отчёта техподдержки, скачанную со страницы «Недельный отчёт» (**Excel**), — в подпапку `tp-weekly/`:
   ```bash
   docker compose cp "Итоговый отчёт ТП.xlsx" app:/data/inbox/tp-weekly/
   ```
   Через полминуты на вкладке «Элементы» — файл со статусом «Ожидает» и планом «без изменений» (данные уже в системе), в папке — `processed/ГГГГ-ММ/Итоговый отчёт ТП.xlsx` и `….result.json`. Отклоните элемент.
7. Откройте «Обзор», «Сквозной отчёт», дашборды трёх служб и PDF-отчёт любой страницы — работают как в 0.3.0.

## После обновления

1. Задайте на рабочем сервере `PUBLIC_URL` (адрес системы для ссылок из Confluence и «По Делу») и `<ВИД>_ALLOWED_HOSTS` для систем, которые будете подключать; при выходе в интернет через прокси — `HTTPS_PROXY`, `HTTP_PROXY` и `NO_PROXY` с внутренними системами («По Делу», «Пульс», 1С), иначе запросы к ним уйдут через прокси. Выполните `docker compose up -d`.
2. Выдайте полномочия «Входящие данные» и «Интеграции» тем, кто будет вести обмен данными без роли администратора («Руководство администратора», раздел «Полномочия»).
3. Выпустите ключи для систем, которые будут присылать файлы (1С, скрипты), и передайте значения их владельцам: «Интеграции → Ключи для входящих вызовов».
4. Подключите системы компании: **Интеграции → Подключить систему** → настройки → **Проверить** → **Создать** → **Включено** и расписание. «По Делу» и «Пульс проекта» — в режиме «Ключ интеграции» с ключами из шага 7 подготовки; проверка покажет версию, ключ и его области и перечислит, чего не хватает. Сначала — с ручным запуском и «Проверить без записи», где это действие есть; расписание включайте после первого удачного запуска. У «По Делу» удобно две записи расписания: структура раз в сутки, файлы из задач каждые 30 минут.
5. Включите «применять сразу» (**Входящие данные → Правила**) для источников и наборов, файлы которых уже несколько раз применены вручную без ошибок.
6. Если папку «Входящие» открыли по сети — проверьте, что 1С и сотрудники могут записывать в подпапки наборов, а файлы после разбора переносятся в `processed/`.
7. Сообщите сотрудникам о новом разделе: «Руководство пользователя», раздел «Входящие данные» (в том числе «Ежемесячный файл службы»); в приложении — «Что нового». Сообщите администраторам новый адрес страницы «Вход по домену» — `/admin/directory`.

## Откат

Откат миграции 0016 сам снимает полномочия «Входящие данные» и «Интеграции» у пользователей (в 0.3.0 их нет). Проверить после отката, что их ни у кого не осталось:

```bash
docker compose exec -T db psql -U dashboards -d dashboards -c "SELECT username FROM users WHERE capabilities::text LIKE '%data.manage%' OR capabilities::text LIKE '%integrations.manage%';"
```

Перед откатом остановите и удалите планировщик: в `docker-compose.yml` версии 0.3.0 его нет, и без этого контейнер `worker` продолжит работать со старым образом.

Предпочтительно — восстановить копию и вернуть 0.3.0:

```bash
docker compose stop app worker && docker compose rm -f worker
docker compose exec -T db pg_restore -U dashboards -d dashboards --clean --if-exists < before-0.4.0.dump
git checkout v0.3.0 && docker compose up -d --build --remove-orphans
curl -s http://127.0.0.1:8000/api/health        # "version": "0.3.0"
```

Если после обновления внесены данные, которые нужно сохранить, откатите схему образом 0.4.0, затем верните 0.3.0:

```bash
docker compose stop app worker && docker compose rm -f worker
docker compose run --rm --no-deps -w /app/backend --entrypoint alembic app downgrade 0015_reports
git checkout v0.3.0 && docker compose up -d --build --remove-orphans
```

При откате схемы теряются элементы входящих и их исходные файлы, правила «применять сразу», подключения с секретами и журналами запусков и ключи для входящих вызовов. Данные, которые входящие и подключения успели записать, — значения показателей, метрики месяцев, недели отчёта, структура и сотрудники — остаются. Системы, которые присылали файлы по ключу, после отката получают 404 — остановите их выгрузку. Том `inbox` с копиями файлов остаётся: удалите его, если он не нужен (`docker volume rm dashboards_serv_inbox`). Пользователи, структура и доступ не затрагиваются; повторно входить не нужно.
