# Нагрузочное тестирование версии 0.2.0: 1000 пользователей

- Дата: 01.11.2026
- Версия: 0.2.0 (структура компании, модель доступа 2.0, вход по домену)
- Стенд, настройки и методика — как для 0.1.0 (`docs/performance/load-test-0.1.0.md`, ADR-0006); сводная статистика — `docs/performance/load-test-0.2.0/`

## Вывод

**Версия 0.2.0 выдерживает 1000 одновременных пользователей на 4 ядрах без ошибок сервера.** Действующий доступ (профиль + личные настройки) вычисляется один раз на запрос без дополнительных обращений к базе, область структуры — по снимку структуры в памяти процесса; оргсхема отдаётся готовым ответом, построенным один раз на ревизию структуры.

| Пользователей | Запросов/с | p50 | p95 | p99 | Ошибки |
| ---: | ---: | ---: | ---: | ---: | --- |
| 1000 | 121 | 16 мс | 53 мс | 180 мс | нет в установившемся режиме (35 тыс. запросов); 3 сброса соединения при разгоне |

## Что изменилось в сценарии

- Пользователи всех уровней демо-стенда 0.2.0: администратор, руководители служб, просмотр, высшее руководство (без исходных записей), руководитель направления, сотрудник (без служб — только «Обзор» и структура). Реестры открывают только те, у кого они есть в меню.
- Новые страницы: «Структура компании» (`/api/org/tree`, вес 4) и карточка сотрудника (`/api/org/people/{id}`, вес 1).

## Разгон

Пока входят все 1000 пользователей (10 входов в секунду, 100 с), медиана входа — 5,7 с (в прогоне 0.1.0 — 2,8 с). Без нагрузки вход занимает 0,33 с для пользователей всех уровней — столько же, сколько в 0.1.0: время уходит на проверку пароля (bcrypt), и при разгоне процессора не хватает. Почему при этом прогоне разгон медленнее, отдельно не выяснялось: машина общая, во время прогона на ней работали и другие процессы. На установившийся режим это не влияет. Реальный утренний пик (вход за 15–30 минут) такой нагрузки не создаёт; рекомендации по массовому входу — в отчёте 0.1.0.
