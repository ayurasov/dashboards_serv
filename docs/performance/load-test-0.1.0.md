# Нагрузочное тестирование версии 0.1.0: 500 и 1000 пользователей

- Дата: 01.11.2026
- Версия: 0.1.0 (решения — ADR-0006)
- Сценарий: `loadtest/locustfile.py`, запуск — `loadtest/run.sh`, сводная статистика прогонов — `docs/performance/load-test-0.1.0/` (Locust, весь прогон с разгоном)

## Вывод

**Версия 0.1.0 выдерживает 1000 одновременно работающих пользователей на 4 ядрах без ошибок сервера.** В установившемся режиме:

| Пользователей | Запросов/с | p50 | p95 | p99 | Ошибки |
| ---: | ---: | ---: | ---: | ---: | --- |
| 500 | 67 | 10 мс | 35 мс | 110 мс | 1 сброс соединения на 14,6 тыс. запросов, ошибок сервера нет |
| 1000 | 135 | 12 мс | 46 мс | 160 мс | 1 сброс соединения на 39 тыс. запросов, ошибок сервера нет |

Узкое место — массовый вход: проверка пароля (bcrypt, ~0,3 с процессорного времени) при 10 входах в секунду занимает три ядра из четырёх. Пока все 1000 пользователей входят (100 с), медиана входа — 2,8 с, остальные запросы в эти секунды замедляются до p95 ≈ 6–11 с. Реальный утренний пик (1000 входов за 15–30 минут, ~1 вход в секунду) этого не вызывает.

## Стенд

- 4 ядра, 15 ГБ памяти; PostgreSQL 16 на той же машине (локальный сокет TCP), генератор нагрузки — там же (на выделенном стенде запас больше).
- Приложение: gunicorn + uvicorn-worker, 9 процессов (2 × ядра + 1), настройки по умолчанию: `DB_POOL_SIZE=5`, `DB_MAX_OVERFLOW=4`, `DB_CONCURRENCY` = 9, `THREADPOOL_SIZE` = 17, `PDF_CONCURRENCY=2`, `RESPONSE_CACHE=true`, `APP_ENV=production`, bcrypt 12 раундов.
- Данные: демонстрационные (`DEMO_DATA=true`) — 7 месяцев службы персонала (48 записей реестра), 109 недель отчёта техподдержки, 1868 заявок Naumen, 142 партнёрства, 6 учётных записей (у каждой — много одновременных сессий).

## Модель нагрузки

Каждый виртуальный сотрудник входит один раз (вход, профиль, службы, палитра) и дальше открывает страницы с паузой на чтение 5–20 с (в среднем запрос раз в 12,5 с). «Страница» — тот же набор запросов API, что делает интерфейс; страницы чужих служб пользователь не открывает. Смесь (вес):

| Страница | Вес | Страница | Вес |
| --- | ---: | --- | ---: |
| Обзор | 10 | Заявки Naumen | 5 |
| Дашборд персонала | 8 | Дашборд партнёрств | 5 |
| Дашборд техподдержки | 8 | Реестр партнёрств | 4 |
| Реестр приёмов и увольнений | 4 | Сопоставление отчёта и Naumen | 2 |
| Сводка персонала | 2 | Сводка партнёрств | 2 |
| Цели персонала | 1 | PDF-отчёт (4 вида) | 1 |
| Ввод показателей месяца (запись) | 1 | | |

Разгон — 10 пользователей в секунду; длительность — 5 мин (500) и 7 мин (1000). Установившийся режим — окна статистики Locust после окончания разгона + 30 с, в таблицах — медиана по окнам.

## Эффект кэша ответов

500 пользователей, тот же сценарий, кэш выключен (`RESPONSE_CACHE=false`):

| Запрос | С кэшем p50 / p95 | Без кэша p50 / p95 |
| --- | ---: | ---: |
| Все запросы | 10 / 35 мс | 15 / 52 мс |
| `GET /api/overview` | 21 / 48 мс | 33 / 64 мс |
| `GET /api/hr/analytics/dashboard` | 20 / 33 мс | 20 / 46 мс |
| `GET /api/tp/naumen/summary` | 8 / 18 мс | 32 / 68 мс |
| `GET /api/partnerships/analytics` | 8 / 14 мс | 12 / 22 мс |

На демонстрационных объёмах выигрыш кэша — в 1,5–4 раза по времени ответа и в процессорном времени (аналитика Naumen пересчитывается по всем заявкам). С ростом данных (десятки тысяч заявок, годы отчётов) доля аналитики в запросе растёт, и кэш становится основным средством держать время ответа: повторные запросы не обращаются к данным службы, пока не изменилась её ревизия.

## Что исправлено по ходу проверки

| Проблема | Проявление | Исправление |
| --- | --- | --- |
| 9 процессов × (10 + 10) соединений больше `max_connections` = 100 | Отказы подключения к PostgreSQL | Пул 5 + 4 на процесс |
| Взаимная блокировка пула потоков и пула соединений | При 1000 пользователях соединения по 100+ с в `idle in transaction`, ошибки `QueuePool limit … timed out`, запросы по 60 с | Очередь запросов к базе (`get_db`) по числу соединений; проверка прав — одна транзакция; закрытие сессии — в отдельном пуле потоков |
| PDF занимали поток и соединение в ожидании очереди | Задержки соседних запросов | Асинхронная очередь PDF до получения сессии |
| Вход держал соединение во время bcrypt | Соединения заняты на 0,3 с на каждый вход | Соединение возвращается до проверки пароля |
| Сценарий нагрузки открывал службы без доступа и не передавал CSRF | Ложные 403 | Сценарий повторяет поведение интерфейса |

Сбросы соединения (`ConnectionResetError`, по одному на прогон) — закрытие keep-alive соединения процессом, который перезапускается по `GUNICORN_MAX_REQUESTS`. Браузер повторяет такие запросы сам; генератор нагрузки — нет.

## Рекомендации

- 500–1000 пользователей: конфигурация по умолчанию на 4 ядрах.
- Больше 1000 или массовый одновременный вход (начало смены, общее совещание): 8 ядер и `WEB_CONCURRENCY` = 9–17 с проверкой `WEB_CONCURRENCY × (DB_POOL_SIZE + DB_MAX_OVERFLOW) < max_connections`, либо несколько экземпляров приложения за балансировщиком (сессии в базе — «липкие» сессии не нужны).
- При перегрузке сервер отвечает 503 «Сервер перегружен» с `Retry-After` через `DB_QUEUE_TIMEOUT` (30 с), а не зависает; рост числа таких ответов в журнале — сигнал добавить процессы или ядра.

## Как повторить

```bash
DEMO_DATA=true docker compose up -d          # или локальный сервер с демо-данными
pip install -r loadtest/requirements.txt
./loadtest/run.sh http://127.0.0.1:8000 500 5m
./loadtest/run.sh http://127.0.0.1:8000 1000 7m
```
