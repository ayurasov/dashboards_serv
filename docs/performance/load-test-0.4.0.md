# Нагрузочное тестирование версии 0.4.0: 1000 пользователей

- Дата: 02.11.2026
- Версия: 0.4.0 (интеграции и входящие данные)
- Стенд, настройки и методика — как для 0.1.0–0.3.0 (`docs/performance/load-test-0.1.0.md`, ADR-0006): PostgreSQL 16, gunicorn с настройками из `backend/gunicorn.conf.py`, кэш ответов включён, демо-данные; сводная статистика — `docs/performance/load-test-0.4.0/`

## Вывод

**Версия 0.4.0 выдерживает 1000 одновременных пользователей без ошибок сервера, с тем же временем ответа, что 0.3.0.** Новые страницы «Входящие данные» и «Интеграции», счётчик ожидающих в меню и приём файлов от внешних систем по API не замедлили остальные запросы.

| Пользователей | Запросов/с | p50 | p95 | p99 | Ошибки |
| ---: | ---: | ---: | ---: | ---: | --- |
| 1000 | 141 | 19 мс | 63 мс | 180 мс | ошибок сервера нет; 8 сбросов соединения на 70,5 тыс. запросов |

Для сравнения, 0.3.0: 144 запроса/с, p50 20 мс, p95 69 мс, p99 180 мс. Значения — медианы по окнам статистики Locust в установившемся режиме (374 окна после разгона); худшее окно — p95 160 мс.

## Что добавлено в сценарий

- **«Входящие данные»** (вес 2) — у пользователей, которым сервер открывает хотя бы один набор (`/api/inbox/datasets` при входе); список с фильтром по статусу.
- **«Интеграции»** (вес 1, администратор): подключения, виды подключений, ключи.
- **Внешняя система** (`InboundSystem`, 2 экземпляра, как 1С или скрипт): ключ интеграции `dash_…`, раз в 30–60 с — файл значений показателей с применением сразу (`POST /api/inbound/v1/files`) и проверка его статуса. Каждое применение меняет ревизию сквозного отчёта — отчёт пересчитывается под нагрузкой.
- `/api/auth/me` теперь возвращает счётчик ожидающих элементов «Входящих» (один `COUNT` по индексу `status, dataset`).

## Время запросов (установившийся режим, медиана по окнам)

| Запрос | Запросов | p50 | p95 |
| --- | ---: | ---: | ---: |
| `GET /api/inbox` | 724 | 25 мс | 67 мс |
| `GET /api/integrations` | 70 | 51 мс | 65 мс |
| `POST /api/inbound/v1/files` (план и применение) | 24 | 41 мс | 41 мс |
| `GET /api/reports/scorecard` | 3277 | 19 мс | 47 мс |
| `GET /api/reports/summary` | 5626 | 19 мс | 56 мс |
| `GET /api/org/tree` | 2119 | 16 мс | 42 мс |
| `GET /api/overview` | 5626 | 39 мс | 110 мс |

`/api/auth/me` и `/api/inbox/datasets` запрашиваются только при входе, то есть во время разгона, когда процессор занят проверкой паролей; без нагрузки — 11 мс (p95 17 мс) и 11 мс (p95 14 мс).

Сбросы соединения (`ConnectionResetError`) — закрытие keep-alive соединения процессом, который перезапускается по `GUNICORN_MAX_REQUESTS`; браузер повторяет такие запросы сам, генератор нагрузки — нет (как в 0.1.0–0.3.0).

## Разгон

Пока входят все 1000 пользователей (10 входов в секунду, 101 с), медиана входа — несколько секунд: проверка пароля (bcrypt) занимает процессор, как в предыдущих версиях. Итоговый код выхода Locust — 1: порог сценария (p95 ≤ 1,5 с) считается по всему прогону вместе с разгоном; в установившемся режиме p95 — 63 мс. Рекомендации по массовому входу — в отчёте 0.1.0.

## Ограничение частоты ключа

С 0.4.0 предел частоты ключа входящих вызовов (`INBOUND_RATE_LIMIT`) общий для всех процессов сервера — счётчик окна хранится в строке ключа и меняется одним `UPDATE`. В сценарии две внешние системы с отдельными ключами укладываются в предел с большим запасом; приём файла с планом и применением — 41 мс.
