# CHANGELOG

## v0.4.0 — 2026-11-02

Интеграции и входящие данные. Любой файл с данными — из папки на сервере, загрузки, от 1С и других систем по API с ключом, из задач «По Делу» и писем — проходит один путь: распознавание набора → план тем же движком, что ручная загрузка → применение сразу (по правилу источника и набора) или после подтверждения; повторы распознаются по SHA-256. Подключения к «По Делу», «Пульсу проекта», Jira, Confluence, Bitrix24, почтовому ящику Exchange и 1С — с проверкой до сохранения, зашифрованными секретами, несколькими расписаниями и журналом запусков; «По Делу» (1.4.5+) и «Пульс» (0.6.0+) — по собственным ключам интеграций «Дашбордов»; фоновую работу выполняет отдельный процесс-планировщик `worker`. Миграция `0016_integrations` только добавляет таблицы, откат поддерживается; новые переменные необязательны, `SECRET_KEY` теперь шифрует секреты подключений. Подробности — [release notes](docs/release-notes/v0.4.0.md), решение — [ADR-0011](docs/architecture/adr-0011-integrations.md).

### Входящие данные

- **Конвейер** ([ADR-0011](docs/architecture/adr-0011-integrations.md)): элемент входящих — источник (папка · загрузка · приём по API · подключение), файл до срока хранения, SHA-256, набор, статус (получен · распознан · ожидает · применён · отклонён · ошибка · повтор), план и итог. Наборы: метрики месяцев и приёмы и увольнения службы персонала, недельный отчёт ТП, заявки Naumen, реестр партнёрств, значения показателей, структура, сотрудники; распознавание по подпапке, выбору, параметру API или содержимому (заголовки, `format` JSON, в том числе `podelu.org-structure` и `podelu.employees`). Повтор — тот же набор и SHA-256 у «живого» элемента.
- **Применение** одной транзакцией от имени источника (все службы и классы данных, `org.manage` и `reports.manage`, без роли администратора и `users.manage`) или пользователя с его правами; правила «применять сразу» для источника и набора; план с ошибками всегда ждёт; перед применением план строится заново (409 `import_has_errors` — ничего не записано).
- **«Входящие данные»** (`/inbox`): список с чипами статусов, фильтрами и сводкой плана, обновление каждые 30 с; карточка элемента — сведения, «Какой это набор?», параметры набора, план любого набора («было → станет», ошибки, решения по сотрудникам), «Применить» / «Отклонить» с причиной / «Повторить» с выбором набора, скачивание исходного файла; «Загрузить файл»; вкладки «Правила» и «Папка» для `data.manage`; счётчик ожидающих в меню; «Входящих пока нет» с четырьмя способами.
- **Папка «Входящие»** (`INBOX_DIR`): подпапки наборов, ожидание дописывания (`INBOX_SETTLE_SECONDS`), атомарный захват через `.work/`, `processed/ГГГГ-ММ/` и `rejected/` с отчётом `*.result.json`, пропуск временных файлов и ссылок за пределы папки; «Проверить сейчас», последний разбор, состояние планировщика. В корне набор распознаётся по содержимому (оценка до 100, имя по шаблону +20, порог 50 — по одному имени файл не распознаётся); столбец «Шаблоны имени: +20 к оценке в корне».
- **Приём по API**: `/api/inbound/v1/ping`, `/files`, `/files/{id}` с ключом `dash_…` (Bearer, без сессии и CSRF), области «Приём файлов» и «Чтение статусов принятых файлов» (подписи — с сервера, `GET /api/integrations/keys/scopes`), `INBOUND_RATE_LIMIT` запросов в минуту на ключ — счётчик окна в строке ключа, общий для всех процессов сервера, `Retry-After` — секунд до конца окна; ключи — выпуск (показ один раз), выпуск заново, отзыв.
- **Срок хранения** исходных файлов обработанных элементов — `INBOX_RETENTION_DAYS` (90 дней), в базе и в папке.
- Загрузки служб: метрики месяцев и реестр службы персонала, реестр партнёрств — `POST …/import` с планом; выгрузка метрик месяцев в Excel; движки ТП и Naumen вынесены в сервисы.
- Значения показателей из файла и от подключений: строка «Очистить» = «да» удаляет сохранённое значение за месяц (действие «Очистится» в плане).

### Интеграции

- **Каркас**: коннектор описывает поля настроек (`string` · `text` · `url` · `password` · `int` · `bool` · `select` · `multiselect` · `list` · `time` · `json` до 64 КБ, `show_if`, подсказки), действия (по расписанию или только вручную), проверку и запуск; запуск пишет данные только через входящие или движки загрузки; журнал запусков (`INTEGRATION_RUNS_KEEP`), состояние подключения, атомарный захват запуска и расписания.
- **Секреты**: шифрование ключом от `SECRET_KEY` (Fernet), привязка к адресу — у «По Делу» к обоим адресам, у почтового ящика к адресу способа подключения — и к подключению; в API — `has_secret`, `secret_fields`, `secret_problem`; «введите заново» при смене адреса и `SECRET_KEY`; вычистка секретов из текстов ошибок, журнала запусков и журнала сервера.
- **Сеть**: адрес `http(s)://узел[:порт][/путь]`, `<ВИД>_ALLOWED_HOSTS` (`.domain` — домен и поддомены), без перенаправлений, тайм-ауты 5/30 с, ответ до 20 МБ, повтор 429/503 только у запросов чтения; прокси `HTTPS_PROXY` / `HTTP_PROXY` с разбором `NO_PROXY` (узел, `.домен` и `*.домен`, `узел:порт` и `IP:порт`, сеть, `*`), ошибка соединения через прокси называет его и подсказывает `NO_PROXY`; IMAP — напрямую.
- **«Интеграции»** (`/admin/integrations`): карточки подключений в порядке видов — состояние, «Включено» только после успешной проверки (409 `check_required`), действия «Запустить», все записи расписания со следующим запуском, «Последняя ошибка» только если она новее последнего успеха, журнал запусков со счётчиками по-русски (`counter_labels`); «Подключить систему»; настройки по схеме коннектора с проверкой несохранённых значений, секретами «задан / заменить / очистить», полями JSON с проверкой при вводе; вкладка «Ключи для входящих вызовов». «Вход по домену» переехал на `/admin/directory`.
- **Расписание**: до пяти записей у подключения, у каждой свои время (интервал или время по дням недели) и действия — например, «По Делу»: структура раз в сутки и файлы из задач каждые 30 минут одним подключением; атомарное занятие только наступивших записей; прежний вид расписания (один объект) принимается. Запуск дольше двух часов — «Запуск прерван» (`interrupted`), подключение можно запустить снова, планировщик отмечает такие запуски в журнале.
- **Confluence — только администратор** (`admin_only`): подключение, публикующее полный сквозной отчёт, создаёт, настраивает, проверяет, запускает и удаляет только администратор (403 `admin_only`); сотруднику с `integrations.manage` карточка видна только для чтения.
- **Коннекторы**: «По Делу» (по ключу интеграции `podelu_…` «По Делу» 1.4.5+ — области `org.read`, `users.read`, `tasks.attachments.read`, `tasks.comment`, без входа учётной записью, курсор задач по активности, комментарий от имени системы «Дашборды» с пометкой «интеграция», недостающие области по действиям в проверке; служебная учётная запись — для версий до 1.4.5; структура через план «Входящих», сотрудники по ID «По Делу» и email, новые — без доступа, отключение отсутствующих; вложения задач списков с данными с пояснением «Задача «…» · автор»), «Пульс проекта» (по ключу `puls_…` «Пульса» 0.6.0+ с правами `projects.read` и `projects.stats`, без `projects.stats` — предупреждение и сопоставление по названию, предупреждение о пределе в 200 проектов; служебная учётная запись — для версий до 0.6.0; пять показателей проектов по подразделениям через «направление → подразделение», светофор проекта, очистка неопределённых значений), Jira (показатели по JQL, Cloud и Server/DC, признаки качества данных), Confluence (публикация сквозного отчёта страницей, одна или еженедельная, финансовые скрыты по умолчанию), Bitrix24 (выручка, выигранные сделки, воронка по ответственным и отделам), «Почтовый ящик (Exchange)» (EWS, Microsoft 365, IMAP; разрешённые отправители, «тема → набор», пояснение «Письмо «…» от …»), «1С (OData)» (запросы к стандартному интерфейсу OData → значения по подразделениям; пример отправки файла из 1С), «Папка «Входящие»». Общее: «Проверить без записи» (значения показателей, которые будут созданы, считаются отдельно — «будет создан при запуске: значений N»), запись только при изменениях, создание показателей после получения данных, обнуление исчезнувших сумм, итоги веток. Понятные ошибки ключей партнёров: не принят, отозван, нет области, лимит частоты, нет API ключей (версия старше).
- `PUBLIC_URL` — адрес системы для ссылок на странице Confluence и в комментариях «По Делу».

### Доступ и администрирование

- Полномочия **`data.manage`** («Входящие данные») и **`integrations.manage`** («Интеграции») — их описания называют доступ к данным (содержимое каждого входящего файла; запись данных от имени подключения; Confluence — только администратор); «Входящие данные» без полномочия — у тех, кто применяет хотя бы один набор, для своих наборов и своих загрузок.
- «Руководство администратора» и «?» на страницах администрирования («Пользователи», «Профили доступа», «Подразделения», «Импорт и экспорт», «Показатели», «Интеграции», «Вход по домену», «Журнал изменений», «Палитры», «О системе») — администратору и сотрудникам с любым полномочием администрирования.
- `/api/auth/me` → `inbox: {available, pending}` — пункт меню и число элементов, ожидающих решения пользователя (с `data.manage` — все, иначе — его наборов).
- Журнал изменений: `inbox_item` (получение, повтор, применение, отклонение, повторная обработка), `inbox_rule`, `integration` (создание, изменение, проверка, запуск, удаление), `inbound_key` (выпуск, выпуск заново, отзыв).

### База данных и миграции

- **`0016_integrations`**: `integrations`, `integration_runs`, `inbound_keys`, `inbox_items` (частичный уникальный индекс «набор + SHA-256» по живым элементам), `inbox_rules`. Рабочий откат: снимает `data.manage` и `integrations.manage` у пользователей.

### Развёртывание

- Сервис **`worker`** в `docker-compose.yml` (`python -m app.cli worker`, тот же образ): папка, расписания, прерванные запуски, очистка, отметка о работе; ждёт схему, по SIGTERM доделывает такт; том `inbox` общий с `app`. Команды `worker [--once]`, `inbox scan`, `inbox cleanup`, `integrations list`, `integrations run` (выключенное подключение — только с `--force`).
- Переменные: `INBOX_DIR`, `INBOX_SETTLE_SECONDS`, `INBOX_MAX_MB`, `INBOX_RETENTION_DAYS`, `INBOUND_RATE_LIMIT`, `WORKER_TICK_SECONDS`, `INTEGRATION_RUNS_KEEP`, `PUBLIC_URL`, `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY` (передаются в `app` и `worker`), `*_ALLOWED_HOSTS`; зависимости `requests`, `cryptography`, `exchangelib` (необязательная).

## v0.3.0 — 2026-11-01

Сквозные отчёты, светофоры и статусы по уровням сотрудников. Статус компании сверху вниз по показателям подразделений — финансовым, операционным и вычисляемым из данных служб — со свёрткой по структуре, объяснением статуса, пропусками данных и заметками руководителей; каждый пользователь видит отчёт в пределах своей области, глубины детализации и классов данных (модель доступа 2.0 начинает действовать полностью). Ввод показателей формой и загрузкой Excel, каталог показателей, PDF, карточка на «Обзоре». Миграция `0015_reports` только добавляет таблицы, откат поддерживается, новых настроек нет. Подробности — [release notes](docs/release-notes/v0.3.0.md), решение — [ADR-0010](docs/architecture/adr-0010-cross-reports.md).

### Сквозной отчёт

- **Показатели** ([ADR-0010](docs/architecture/adr-0010-cross-reports.md)): каталог с классом данных, направлением, свёрткой (сумма · среднее · без свёртки), правилом светофора (пороги или отклонение от цели в %), целью по умолчанию, источником (вводится службой-владельцем или вычисляется из данных служб) и типами уровней, где значение ожидается. Вычисляемые: приём и увольнение по подразделениям, текучесть, время закрытия позиции, заявки в работе, решено, решено/получено, доля партнёрств «в норме».
- **Расчёт**: значение — собственное или свёртка вложенных; статус подразделения — худший из показателей и вложенных; объяснение — где возникла причина; пропуск ожидаемого значения — «Нет данных» и критичное нарушение полноты без ухудшения статуса. Расчёт за период — один раз на ревизии структуры, данных служб и значений, затем отбор под пользователя; 6 SQL-запросов на ответ независимо от размера структуры.
- **Доступ по уровням**: вершины — область пользователя; глубина детализации — ниже только свёртка и «детализация недоступна»; показатели недоступных классов не возвращаются и не влияют на статус и объяснение — «статус по N доступным показателям»; ссылки на дашборды и реестры служб — по правам; PDF — по праву на выгрузку.
- **«Сквозной отчёт»** (`/reports`): статус вершины крупно, «почему такой статус», подразделения по статусам, нарушения полноты с «Заполнить», заметки, «Ваш доступ: …» и скрытые классы; **матрица** «подразделения × показатели» (цвет, значение, изменение к прошлому месяцу, подсказка с целью, отклонением, источником и комментарием, «Нет данных», замок детализации, фильтры по статусу и «Только с нарушениями»); **оргсхема статусов**; **список** для телефона; **панель подразделения** с трендом за 12 месяцев и целью, вложенными подразделениями, переходами к службам и «Открыть ветку».
- **Отметка «под контролем»** руководителя подразделения за месяц с комментарием; расчётный статус не меняется.
- **«Ввод показателей»** (`/reports/entry`): подразделения × показатели за месяц — значение, цель, комментарий; сохраняются изменённые ячейки, всё или ничего, ошибки у ячеек; выделение обязательных незаполненных; загрузка Excel/CSV (проверка → план → применение) и шаблон CSV; без права ввода форма не запрашивается — страница объясняет, кто вводит.
- **«Показатели»** (`/admin/indicators`): каталог по классам данных, редактор с предпросмотром светофора и проверкой значения, выключение и удаление (со значениями — после подтверждения), «Подразделения служб».
- **«Обзор»**: карточка статуса области пользователя; **PDF** сквозного отчёта (альбомный, по 6 показателей на таблицу).
- Меню: «Сквозной отчёт» для всех, «Показатели» в администрировании; пункты меню не сжимаются при переполнении; нижняя панель на телефоне для боковых панелей.

### Доступ и администрирование

- Полномочие **`reports.manage`** («Ведёт сквозные отчёты»): каталог показателей, ввод значений любой службы во всех подразделениях, заметки о статусе любого подразделения.
- Ввод значений — уровень «Ввод данных» к службе-владельцу показателя (в том числе к службе без дашборда) в своей области структуры.
- Журнал изменений: показатели, значения и загрузки, заметки, подразделения служб.

Подробности — [release notes](docs/release-notes/v0.2.0.md), решения — ADR-0007…0009 в [docs/architecture](docs/architecture), проект сквозных отчётов 0.3.0 — [ADR-0010](docs/architecture/adr-0010-cross-reports.md).

### Структура компании

- **Данные** ([ADR-0007](docs/architecture/adr-0007-org-structure.md)): дерево подразделений (тип уровня, порядок, код, внешний идентификатор, источник), руководители с основным, у пользователя — основное подразделение, явный руководитель и «первое лицо»; имена уникальны среди соседних частичными уникальными индексами (без гонки параллельных запросов); типы уровней, предел вложенности и вид оргсхемы — в `app_settings`.
- **Правила подчинения**: «первое лицо» → явный руководитель → основной руководитель подразделения с подъёмом по дереву; проверки циклов, вложенности, имён и кодов с понятными сообщениями; признак основного руководителя не теряется; удаление подразделения — только без вложенных и с записью в журнал.
- **Снимок структуры** в памяти процесса по ревизии `org_revision`; `/api/org/tree` отдаёт все виды одним ответом, тело строится один раз на ревизию.
- **«Структура компании»** (`/org`): оргсхема, «Люди», дерево, таблица; общий поиск, «Уровней», «Развернуть / Свернуть», «Где я», масштаб, «Вписать» и перетаскивание; выбранное и вид — в адресе; боковая панель подразделения и сотрудника, у ведущих структуру — подчинение, должность и история.
- **«Подразделения»**: дерево с численностью и руководителями, добавление вложенного, изменение и перенос, руководители, удаление, «Типы уровней и вложенность».
- **«Импорт и экспорт»**: структура (JSON `dashboards.org-structure` v1), сотрудники (Excel, CSV, JSON; разбор различий «Система / Файл / Объединить / Своё», вопрос «тот же человек?»), быстрая загрузка списком, Active Directory — проверка → план → применение одной транзакцией; ничего не удаляется, руководители только добавляются.

### Доступ и пользователи

- **Модель доступа 2.0** ([ADR-0009](docs/architecture/adr-0009-access-model.md)): профиль доступа + личные настройки + уровни служб (в том числе «нет доступа»); область структуры (вся компания · своя ветка · своё подразделение, своя у службы), дополнительные подразделения, классы данных (операционные · персональные · финансовые), глубина детализации, исходные записи, выгрузка; действующий доступ с источником каждого значения.
- **Встроенные профили**: «Высшее руководство», «Руководитель направления», «Руководитель подразделения», «Специалист», «Сотрудник»; «Профили доступа» — карточки, редактор, сравнение; удаление используемого профиля — 409 с числом пользователей.
- **Проверки на сервере**: реестры и карточки — право на исходные записи; ФИО и причины увольнения — класс «персональные»; все выгрузки Excel/CSV/PDF — право на выгрузку; светофор записей партнёрств считает сервер, поэтому дашборд работает без доступа к записям; ключи кэша ответов учитывают область, классы данных и записи.
- **Полномочия** `org.manage` и `users.manage` — часть администрирования без роли администратора; администраторов изменяет только администратор.
- **«Пользователи»**: сводка и фильтры в адресе (роль, статус «без доступа», подразделение, профиль, способ входа), создание с паролем, входом по домену или без доступа, «Выдать доступ», сброс пароля («Перевести на пароль системы» для домена), удаление с предложением отключить; карточка с вкладками «Профиль», «Доступ», «Полномочия», «Журнал».
- **Интерфейс по правам**: недоступные разделы и кнопки скрыты, «Нет доступа» объясняет причину, профиль — «Мой доступ» простыми словами, в меню под именем — профиль доступа.

### Вход по домену и Active Directory

- **LDAP** ([ADR-0008](docs/architecture/adr-0008-users-ldap.md), ldap3): служебная привязка, поиск с экранированием логина, привязка от имени найденной записи, отключённые в AD не входят, LDAPS и StartTLS с проверкой сертификата; сопоставление по идентификатору каталога, идентификатору синхронизации AD и e-mail; создание при первом входе с профилем по группам каталога; 503 «Сервер домена не отвечает» для доменных учётных записей; пароль доменной учётной записи в системе не хранится.
- **«Вход по домену»**: состояние подключения, шифрование, создание учётных записей, профили по группам, замечания настройки, проверка подключения и поиск учётной записи без пароля сотрудника.
- **Синхронизация с AD** (`AD_SYNC_*`): постраничное чтение, путь подразделения из атрибутов или OU, руководитель из `manager`, руководители подразделений по подчинённым; отключаются только пришедшие из AD, включение не выполняется никогда. CLI для планировщика: `python -m app.cli org-sync (--ad | --csv ФАЙЛ) [--apply] [--create-missing] [--deactivate-missing] [--actor] [--json]`, коды выхода 0/1/2.
- Страница входа: подсказка домена, сообщения «сервер домена не отвечает» и «учётной записи нет».

- **`0012_v0_1_0_schema`** перестраивает все таблицы с переносом данных и устойчива к любому прежнему состоянию базы (Docker с историей Alembic, локальная без неё, пустая): префиксы `hr_`/`tp_`, общая `traffic_light_rules`, справочник `services`, `service_access`, `user_sessions`, `service_settings`, `data_imports`; год и неделя отчёта ТП — целые и уникальные, номер заявки Naumen уникален; единая конвенция имён ограничений, внешние ключи с каскадами, CHECK-ограничения, индексы под фильтры.

- **Персонал**: дашборд одним запросом (динамика к прошлому месяцу, цели, воронка найма, светофор по месяцам, разрез по подразделениям); реестр приёмов и увольнений с фильтрами, причиной увольнения и выгрузкой в Excel; ввод данных месяца с сохранением только изменённого; сводка по месяцам, кварталам, полугодиям и годам; цели; пользовательские дашборды.
- **Техподдержка**: дашборд недельного отчёта на ECharts; недельный отчёт с проверкой уникальности недели; загрузка xlsx/csv в режимах «Дополнить» и «Заменить», выгрузка в формате исходного отчёта; сравнение периодов; заявки Naumen — загрузка с сопоставлением по номеру, аналитика; сопоставление отчёта и Naumen.
- **Партнёрства**: светофор каждой записи (худший из статуса, NDA, соглашения и срока сертификата); реестр с фильтром по светофору; аналитика; сводка по годам; хронология; правила светофора; выгрузка в Excel.
- **Светофор** персонала и техподдержки — общая страница настройки с проверкой порогов.
- **Журнал загрузок** файлов (кто, когда, сколько добавлено и обновлено) — в обзоре и на страницах служб.

### Администрирование

- Пользователи: поиск и фильтры, карточка с профилем и матрицей доступа к службам, временный пароль, отключение с завершением сессий; подразделения.
- Журнал изменений: фильтры, постраничный вывод, значения «до» и «после», выгрузка CSV.
- Палитры: предпросмотр, встроенные палитры, своя палитра; «О системе»: версия, схема базы, объёмы данных.

### PDF-отчёты

- Единый оформитель отчётов: шапка, фильтры, плитки показателей, таблицы со светофором, графики в цветах палитры.
- Шрифт DejaVu из состава matplotlib — в slim-образе Docker кириллица в PDF раньше ломалась.
- Новые отчёты техподдержки (недельный отчёт, заявки Naumen): раньше кнопка PDF на страницах ТП обращалась к несуществующим отчётам.

### Производительность

- Кэш готовых ответов аналитики в памяти процессов с ключом по ревизии данных службы: изменение данных в одном процессе сразу видно во всех; учитывает ограничение «свои подразделения».
- **Очередь запросов к базе**: сессию получают не больше запросов, чем соединений в пуле процесса (`DB_CONCURRENCY`), остальные ждут без потока и соединения; дольше `DB_QUEUE_TIMEOUT` — ответ 503 «Сервер перегружен» с `Retry-After`. Исправляет взаимную блокировку пула потоков и пула соединений, из-за которой при 1000 пользователях запросы зависали на 30–60 с.
- Проверка сессии, CSRF и прав — одна транзакция; вход возвращает соединение до проверки пароля; PDF-отчёты строятся не больше `PDF_CONCURRENCY` одновременно в асинхронной очереди.
- Пул соединений PostgreSQL 5 + 4 на процесс (9 процессов укладываются в `max_connections` = 100), gunicorn с перезапуском процессов, сжатие ответов (готовые ответы кэша хранятся сжатыми).
- Нагрузочный сценарий Locust (`loadtest/`). **1000 одновременных пользователей на 4 ядрах: p50 12 мс, p95 46 мс, без ошибок сервера**; 500 — p50 10 мс, p95 35 мс — [отчёт](docs/performance/load-test-0.1.0.md), [ADR-0006](docs/architecture/adr-0006-performance.md).

### Исправлено

- Гонка при ленивом создании настроек ТП (500 на дашборде ТП при одновременных запросах).
- Поиск по кириллице без учёта регистра в SQLite.
- `NaN` в наборах данных Naumen.
- Пустой только что добавленный месяц больше не обнуляет карточки дашборда.
- Имя скачиваемого файла: в части браузеров файл сохранялся под именем «download»; для старых клиентов имя латиницей.
- Ошибки полей формы показываются рядом с полями, без повторного всплывающего уведомления.
- Короткая палитра графиков заполняет все семь цветов; приглушённый цвет бренда применяется.

### Сборка, CI, тесты

- Docker: многостадийный образ, непривилегированный пользователь, проверка здоровья без curl, миграции перед стартом; compose с PostgreSQL и проверкой готовности.
- GitHub Actions: сервер (ruff, pytest с PostgreSQL 16, миграции с нуля), интерфейс (ESLint, Vitest, сборка), e2e (Playwright на демо-данных).
- Сервер: pytest — вход и сессии, матрица доступа, службы, импорт и экспорт, PDF, журнал, кэш, миграции на SQLite и PostgreSQL (совпадение схемы с моделями, обновление баз прежних версий). Интерфейс: Vitest для утилит и предметной логики, Playwright — сквозные сценарии.
